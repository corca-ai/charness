# Proof-Path Efficiency

Use this reference when a standing proof path is slow and the candidate fix
changes a runner, wrapper, process boundary, validator route, fixture runtime, or
parallel execution policy.

## Preserve Proof Before Optimizing It

Remove redundant startup, discovery, parsing, or orchestration before removing
proof. Keep the smallest real delivery-boundary smoke that can exhibit packaging,
process, protocol, or installation failures; push repeated behavior assertions
below that boundary when honest.

For a material proof-path change, write the comparison card before
implementation. Tiny reversible cleanup can use the same questions inline:

- workload identity: same targets, selection, environment, isolation, and proof semantics
- ownership: the selector owns *what* runs; the canonical executor owns *how* it runs
- compatibility envelope: inputs/argument boundaries, state/lifecycle, outputs,
  failures/exits, and the retained real-boundary smoke
- consumption proof: one representative changed/new input is actually read by
  the selected validator or consumer; routing output alone is not proof
- evidence: baseline and candidate exact commands, outcomes, and comparable
  timing; use a break-even judgment instead of assuming parallelism or a new
  process helps tiny workloads

## Interpretation

An equal-workload speedup supports an execution-shape claim, not a coverage
claim. A broad final gate after mutation lock can still be the correct backstop;
do not label it waste merely because focused feedback became faster.

Do not preserve retired implementation formatting, traceback text, or internal
log layout merely because the old helper emitted it. Preserve only behavior a
current consumer uses, and prove that consumer directly.
