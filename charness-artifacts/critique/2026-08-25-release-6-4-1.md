Date: 2026-08-25

Whether to publish Charness `6.4.1` as a patch release from `v6.4.0`, carrying
the consumer-friction proof, identity, diagnostic, goal-readiness, and

validation of existing public flows, preserves public command and install

## Release Scope

- Target version/tag: `6.4.1` / `v6.4.1`.
- User-visible outcome: proof surfaces no longer turn missing, stale, or
  mis-bound evidence into a stronger verdict than the observation supports.
- Included correction groups: subject/path identity, debug and artifact
  diagnostics, goal readiness and lifecycle evidence, mutation/TAP accounting,
  capability-envelope and reviewer delivery binding, and checked-in
  source/plugin parity.
- Not claimed: live provider behavior, universal host/Ceal end-to-end adoption,
  Cautilus evaluation, or a new public external-worker command/install surface.

## Surface-Lock Inventory

- Source Python and tests: exact-HEAD standing quality and focused tests.
- Public/support skill exports: root source and checked-in plugin copies must be
  synchronized by `scripts/sync_root_plugin_manifests.py`.
- Packaging manifests: all plugin and marketplace versions must agree at
  `6.4.1` after the bump.
- Release record and notes: generated only after the version mutation, then
  audited by a distinct claims-review record before the tag is pushed.
- Fresh checkout: the five configured probes must run against the final
  prepared tree; this is source-checkout proof, not installed-host proof.
- Installed/host boundary: post-publish `charness update`, `charness version`,
  and `charness doctor` readbacks remain explicit evidence obligations.

## Failure Angles

- Operational: process-exit success must not substitute for a typed quality
  receipt, parity, fresh-checkout, or public readback verdict.
- Communication: “consumer-friction fixes” must be decomposed into outcomes,
  proof boundaries, open items, and a patch-level rationale.
- Humane interface: first readers need one stable command shape, explicit
  update/restart/rollback guidance, and structured `next_action`/
  `session_staleness` interpretation.
- Irreversible boundary: the release record, claims review, tag, push, and
  installed refresh must each retain their own evidence channel.

  typed `pass` quality receipt. Before tag/publication, consume the receipt and
  require `status: pass` with no unproven subjects, or stop and repair that
  release-gate contract.
- Bundle: release notes should lead with the proof-boundary problem, group
  corrections by consumer outcome, state patch-not-minor rationale, and give
  update/restart/rollback instructions.
- Valid but defer: final `6.4.1` record, generated parity, and fresh-checkout
  evidence are produced by the normal post-bump prepared-stop workflow.
- Valid but defer: installed/Ceal/provider/host evidence is post-publish and
  must remain a non-claim until adapter-declared readbacks run.
- Over-worry: universal host proof is not required; the full changed-path
  trigger evaluation returned `required: false`.
- Over-worry: the first attempt's runtime-path boundary failure is an invalid
  review-window setup, not evidence about the release code.
