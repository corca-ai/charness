Whether the current `6.2.0` source candidate should be versioned and published as
`6.3.0` / `v6.3.0`, with #670's consumer-facing validator discovery capability as
the minor-bump trigger.

## Failure Angles

- Gawande / release-boundary integrity: the saved planner receipt is targetless,
  and the current adapter's managed install, version, and doctor proof has not
  been established. A passing source checkout is not packaged-candidate proof.
- Minto / contract and claim integrity: the goal promises stable IDs, artifact
  type, adoption policy, documented doctor/inventory exposure, and a declaration
  of `wired` or non-empty `opt_out_reason`; the live catalog/checker validates a
  smaller path-indexed shape. The goal's `132/13` verification counts are also
  stale against the live `133/14` result.
- Raskin / wrong-owner and consumer reachability: the validator catalog has no
  documented consumer discovery path, and `charness catalog list` succeeds for
  `/definitely/not-a-repo`, proving that one nearby inventory surface can answer
  from the wrong owner instead of refusing the supplied root.
- Counterweight / decision quality: the JSON packet identity is authoritative;
  the different Markdown digest is not a blocker. The missing release artifact
  at `6.3.0` is expected before release mutation, and the external doctor
  temporary-directory observation is not a product defect.

## Counterweight Pass

The counterweight confirms a `HOLD`, not a rejection of the underlying additive
catalog work. Three findings must be acted on before shipping: bind a fresh plan
to `6.3.0`/`v6.3.0` and the current candidate evidence; either complete #670's
promised consumer contract or explicitly narrow and rebind the release scope;
and execute the adapter's managed `charness update`, `charness version`, and
`charness doctor` proof after a candidate is prepared.

The wrong-owner capability-inventory behavior is a real failure smell, including
because the user explicitly includes wrong paths and calls in the standing rule,
but it is a separate capability-inventory contract from the validator catalog.
It remains a named structural follow-up rather than evidence that the current
validator checker itself accepts a missing catalog. The resume publisher's
missing release-surface gate is also real and remains pre-existing; it becomes a
release blocker if the resume path is used.
