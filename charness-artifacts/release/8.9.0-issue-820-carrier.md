Let Node mutation cases require the intended named test failure (#820)

Closes #820

Classification: feature

JTBD: A downstream repository (Ceal #830) must retire its small declarative
guard-mutation runner in favor of Charness, which requires proving that the
intended named test failed — not merely that the Node test command went red.

Boundary: In scope is one declarative expected-failing-test identity for
Node/TAP execution through the existing reporter seam, with kill/refuse/
survive semantics and byte-for-byte source restoration. Out of scope are
pytest named-failure listing (counts-only by design, refuses instead),
production caller reachability for .js targets (explicit non-claim), and
interrupted-journal recovery simulation (open risk, deferred).

Resolution Brief: A plan entry may set `expected_failing_test` to one TAP
test name; the mutant kills only when that name is among the run's owned
not-ok results, refuses when the command fails without it, and still
survives a green run. Unusable expectations and name-requiring pytest plans
refuse rather than guess.

Implementation: New `scripts/mutation/mutation_expected_failure.py`
(plan/run contract); failing-test names on the node-test reporter
(`scripts/mutation/mutation_test_reporters.py`); `expected_failing_test`
payload field through `mutate_and_restore.py` classification and
`mutation_sweep_report.py` rendering; standing tests including a real
`node --test` sweep (`tests/quality_gates/test_mutation_test_reporters.py`,
85 passing). Shipped in charness 8.9.0 (minor: additive, no migration).

Prevention: The named-failure contract lives in one module with
parse/match/refusal owned together; templated empty or non-string
expectations raise instead of coercing; the spec-reporter refusal names
the one-flag fix; the sweep payload renders each mutant's declared
expectation for audit.
