# Charness v8.15.0

## What changed

- `charness task run` no longer stops a lane on a wall clock by default. A progress rule bounds every lane instead. A window of `CHARNESS_TASK_RUN_PROGRESS_WINDOW_SECONDS` (default `1200` seconds; `0` turns the rule off, and a negative value falls back to the default) can pass with no new commit, no file change, and no new command result. When that happens, charness interrupts the executor and resumes its session with a checkpoint request: commit what is coherent and report, reply `BLOCKED:`, or keep going. If the next window also shows no progress, charness stops the lane itself (`NO-PROGRESS-STOP:`). No human or orchestrator has to watch for the stop to happen. A test, lint, or typecheck command rerun with the same text on an unchanged tree is not progress. On its 3rd run the lane is asked to switch to the debug skill, on its 4th to checkpoint, and on its 5th the lane is stopped. A command younger than one window is never killed. A command still running a window later can be killed, so set the window above the longest command a lane legitimately runs. Codex resume after this kill was probed live. Muse resume after a kill was not probed, and a Muse lane whose resume fails is relaunched in place in the same worktree. `--timeout-seconds` still works as an explicit hard cap, but it no longer has a default. `progress_guard.progress_rule` and `execution.preemptions` in the task result record every check, every message, and every stop. `task status` shows the live window state.
- Executor lanes that `charness task run` launches now have network access inside their workspace-write sandbox. Codex lanes get `-c sandbox_workspace_write.network_access=true` and Muse lanes get `--sandbox-network enabled`. Before this, the lane sandbox refused tests that bind a local port or fetch through the proxy, with `listen EPERM` or a proxy `502` response. The release tests check the flags the carrier passes, not a bind or fetch inside a sandbox. Read-only review sandboxes are unchanged.
- `charness task run` now stamps each JSON-object line of a lane's `<executor>.events.log` with `charness_received_at`, the UTC time the carrier received that line from the executor's pipe. Before this, Codex items and Muse envelopes carried no wall time, so a lane could not say how long a command or phase took. Non-JSON lines are unchanged, and so are the rest of each event's bytes.
- `charness task status <task-id> --commands` reads that stamped log back and reports the lane's longest commands, how many commands it started in each family (test, lint, typecheck, merge), and its time per phase. The option is refused without a task id. Durations are receive-time estimates. Pipe buffering makes them upper bounds on the executor's own timing. A stamp without a timezone counts as unstamped. A lane run before this release has an unstamped events log, so for that lane the report counts command starts but gives no durations or phase times.
- Stamping never loses event bytes silently. Every byte the executor writes before its pipe closes reaches the events log, on normal exit, timeout, interrupt, and preemption. Charness adds only the stamp field on JSON lines and a newline after an unterminated final line. Some loss can still happen: a descendant process may keep the pipe open past the process-group kill, or a log write may fail. Either case is recorded in the task result as `execution.event_capture_incomplete`. The reader keeps draining the pipe, so the executor never blocks on a full pipe.
- The debug skill names a follow-up record after the lane or branch that writes it. On a `task/<lane>` branch the record is `<date>-debug-review-followup-<lane>.md`, and any other non-default branch, or a lane id that is not already a lowercase slug, gets a short hash of the branch appended. Before this, every follow-up was named by counting the files in its own worktree, so parallel lanes picked the same number and their merges collided. On a default branch or a detached HEAD the counter remains. The `latest.md` pointer works as before, so parallel lanes that each write a follow-up can still both change `latest.md`.

## Update

Run `charness update`, then run `charness version` to confirm the installed version. No migration is required. A launcher that passes `--timeout-seconds` keeps that hard cap until it drops the flag. To rely on the progress rule alone, drop the flag. Set `CHARNESS_TASK_RUN_PROGRESS_WINDOW_SECONDS` above the longest command your lanes legitimately run if that exceeds the default. `--no-progress-seconds` is still the separate first-edit budget for require-change lanes, not the progress window. Lanes now have network access, and this release has no per-lane switch to turn it off.
