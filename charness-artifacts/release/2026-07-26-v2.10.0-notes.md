# charness 2.10.0

Two gates learned something about the machine they run on: one now measures the
CPUs your process can actually use, the other stops blocking on a temp root it
does not own. Both change a verdict on upgrade, so read the first section.

## Changed verdicts (read this before upgrading)

**`check-runtime-budget` can newly fail on an affinity-restricted machine.**
The runtime profile id is now derived from `sched_getaffinity` rather than
`os.cpu_count()`. A run under `taskset`, a cpuset, or `docker --cpuset-cpus` used
to file its samples into the unrestricted profile — dragging that profile's
median toward its bar with numbers from a machine that was never available. It
now lands in an id matching the cores it really had.

Two consequences on upgrade:

- **If your adapter populates `runtime_budget_profiles`**, the newly derived id
  may not be a key in it. That is a `profile_config_errors` entry and
  `check_runtime_budget` exits **1** — a run that was green in 2.9.0. Add the new
  id (run the gate once to see which) or leave `runtime_budget_profiles` empty.
- **Existing samples under the old id are orphaned.** The first post-upgrade run
  on such a machine reports every budget as `no-sample`, which is a WARN, not a
  failure. It clears as samples accumulate.

A repo that has never populated `runtime_budget_profiles` — including every
repo bootstrapped from the default adapter, which renders `{}` — is unaffected.

**`check-seed-fixture-budget` blocks less than 2.9.0 said it would.** 2.9.0
announced that a failed `du` scan stops exiting 0. That still holds, with one
carve-out added here: a **direct** invocation with `PYTEST_DEBUG_TEMPROOT` unset
is scanning a temp root the repo does not own, and a stranger's files in
`/tmp` are not evidence about your fixtures. That case is now
`advisory_only_unowned_temp_root` and exits 0. Inside `run-quality.sh`, which
sets the temp root, nothing changes.

## Added

- `skills/public/quality/scripts/dup_ratchet_rebaseline.py`: scoped baseline
  rebaselining for the dup ratchet, split out of `check_dup_ratchet.py`.
- `--restamp-tool-version` on `check_dup_ratchet.py`. A `nose` version bump
  regroups clone families, so the drifted fingerprints are scanner skew, not new
  duplication — but a blanket `--write-baseline` also absorbs any genuinely new
  family sitting in the same run. This flag re-stamps **only** the scanner
  version, and refuses when the family set actually moved.

## Fixed

- The `du` capability probes are now measured against real GNU and BusyBox
  binaries rather than assumed wordings.
- Combining two dup-ratchet baseline-mutation modes in one invocation is now a
  usage error (`exit 2`) instead of silently applying the first and leaving the
  operator in a loop.

## Why minor rather than patch

The behavior repairs alone would be a patch. The new public module and the new
operator flag on an exported gate are additive operator surface, which the
version policy puts at minor — the same call 2.9.0 made for the same shape.

## Not in this release

Four of the seven commits since 2.9.0 reach no installed user and are listed
here only so their absence is not read as an omission: a test-only assertion
sweep over previously unasserted rejection and renderer lines, a handoff refresh,
the 2.9.0 verification record, and a CI-workflow change giving a direct push to
`main` the changed-line signal it lacked. None of them ship in the plugin export.

## Known limits

- `sched_getaffinity` is wrapped in `except AttributeError` only. It can raise
  `OSError` under some restricted sandboxes, which would crash the gate on a host
  where `os.cpu_count()` could not fail. Unreproduced, not yet fixed.
- `--restamp-tool-version` is not yet described in the dup-ratchet reference.
- The `du` `illegal option` wording used by BSD/macOS builds is still assumed
  rather than probed against a real binary.
