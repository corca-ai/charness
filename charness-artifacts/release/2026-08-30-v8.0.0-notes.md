# Charness 8.0.0 — composable capability, less avoidable rework

## Summary

Charness 8.0.0 removes several known Charness-owned sources of duplicate work
and ambiguous handoff while making repository analysis and review inputs more
composable. It does not claim that consumer repositories are already faster in
production, or complete removal of known friction.

The main consumer-facing direction is narrower ownership: Charness supplies
typed capabilities, evidence, and refusals; the consuming repository's agent
composes those capabilities with its own Git layout, worktrees, submodules, and
development workflow.

## What changed

### One bounded task lane

- `charness task run` owns a complete isolated lane: clean-parent preflight,
  named worktree creation, external runtime/cache roots, Luna execution,
  terminal result delivery, and separate tracked, untracked, and ignored
  residue verdicts.
- The task model is fixed to `gpt-5.6-luna`; the orchestrator selects a bounded
  effort level.
- `charness task status` reads the external result store without creating a
  repository-local scheduler or inferring parent state.
- The old parent-level task spelling, backend/model override flags, and
  repository-local claim/submit/review/abort envelope lifecycle are removed.

### Smaller workflow ownership

- `achieve` owns active Goal Run planning, cursor navigation, and lesson
  selection without requiring the full issue graph for routine pickup.
- Standalone handoff state, session hooks, progress mirrors, Cautilus coupling,
  and automatic release retros are removed.
- Critique uses materially different reviewers where the decision warrants it;
  ordinary reversible implementation does not inherit an unconditional
  fresh-eye or closeout-artifact tax.
- Goal Run activation preserves the exact live parent Markdown while adding its
  managed metadata. After activation, parent updates preserve human Markdown
  by default; an amendment requires a canonical authorization receipt binding
  the parent, Goal Binding, live and desired body hashes, and explicit approval
  evidence. Immutable Goal identity fields and complete provider readback remain
  enforced.
- Release and closeout keep distinct-observer evidence at irreversible
  boundaries without replaying the full carrier matrix.

### Composable repository-analysis and review capability

- A typed native `repograph` capability now supplies migrated inventory,
  classification, reverse-reader, standalone-target, plugin-reference, and
  export-safe facts to Charness gates without each consumer rebuilding those
  facts in Python.
- Critique packet selection has one changed-path owner across merge, rename,
  deletion, non-ASCII, staged, worktree, and non-blob shapes.
- Commit- and range-bound review inputs carry exact semantic bytes, including
  deleted-file preimages, to the Codex and Claude reviewer backends. Empty,
  mismatched, unavailable, or oversized input refuses before launch.
- Default committed-ref mismatch now reports declared, changed, missing,
  unexpected, and auto-excluded paths and points to the explicit manifest
  route, while keeping exact identity and avoiding packet self-inclusion.
- Reviewer execution has one backend owner and a typed lifecycle that preserves
  identity-bound partial progress across timeout or interruption without making
  partial output approval-eligible.

### Fewer false or opaque development loops

- Duplicate-ratchet summaries project the same nonempty document-family count
  and samples that caused the underlying verdict.
- `worktree prepare` skips setup when the selected doctor explicitly covers the
  declared skipped responsibilities; a generic doctor pass no longer creates
  false readiness.
- Backend command construction and normalization no longer have duplicate owners.
- Release runs cheap checks before the later release-only proof and keeps
  broader mutation tooling out of ordinary implementation.

### Release install observation moved after publication

- The broad pre-publish real-host detector and manual checklist are retired.
  They triggered on common source changes that did not alter install behavior.
- After GitHub publication, the release helper runs `charness update`, reads
  `charness version`, and runs `charness doctor`. It records mismatch,
  unavailability, and command failure instead of converting them to success.
- These observations can detect a bad installed release after publication; they
  do not prevent publication. The rollback below remains the operator recovery
  path.

### Release evidence authoring owns its derived facts

- The claims-review scaffold derives the prepared commit, release-record identity,
  target/tag, previous release, and exact full changed-path digest from the prepared
  tree. Reviewers no longer hand-copy repository-owned bindings into JSON.
- The versioned v4 claims-review schema is closed: removed or unknown state is
  refused instead of surviving unnoticed in a resume carrier or renderer.
- Resume classification derives generated artifact scope from the release
  adapter's record path, so consumer-owned output directories and root records
  do not fall out of the recovery state machine.
- Plugin packaging now names its untracked host output a materialized export:
  release adapters use `materialized_plugin_root`, and packaging manifests use
  `materialized_source_path`. Export validation reads the bytes hosts actually
  consume instead of asking Git to enumerate an intentionally ignored tree.
- Preview is read-only. With `--write`, the scaffold's write target is the review
  JSON; reviewer independence and the final publish decision remain separate
  evidence boundaries.

## Upgrade

1. Run `charness update`.
2. Confirm `charness version` reports `8.0.0`, then run `charness doctor`.
3. Restart the Codex or Claude session so the refreshed plugin cache is loaded.
4. Remove local automation that uses the retired parent-level task spelling,
   task-envelope lifecycle commands, Charness session hooks, the standalone
   handoff surface, or Charness-owned Cautilus integration.
5. Keep consumer-owned wrappers for repository-specific topology or behavior
   that the host spawn API and composable Charness capabilities do not own.
6. Maintainer repositories with a release adapter or packaging manifest should
   rename `checked_in_plugin_root` to `materialized_plugin_root` and
   `checked_in_source_path` to `materialized_source_path`.

## Rollback

Reinstall or pin `v7.0.0` through the host's normal plugin-install mechanism,
then restart the host session. `v8.0.0` does not read retired repository-local
task-envelope state, so preserve a separate copy if you may intentionally roll
back.

## Known residuals and non-claims

- No empirical consumer-development speedup is claimed. This release establishes
  removed rework paths and composable capability, not production timing data.
- An identical local standing selection confirms materially fewer synchronous
  Git and Python launches after operation snapshots, immutable fixture seeds,
  and explicit process-boundary test ownership. This is structural evidence of
  removed repeated work, not an empirical consumer-development speedup claim;
  remaining delivery-boundary and semantic repository reads are not claimed
  eliminated.
- Hosted Mutation Tests did not reach mutation during Goal #744 because the
  workflow failed in its standing baseline. The authoring-clone versus
  provider-history referent seam is now repaired through complete HEAD ancestry
  and exact candidate-bound local-context declarations, but no mutation score,
  success, or non-regression claim is made.
- External worker admission lacks the planned installed-versus-source
  implementation identity check from issue #715. A source repair alone does
  not prove that an already installed `impl` skill adopted the same bytes.
- `repo_file_listing.py` and `surfaces_lib.match_surfaces` remain explicit
  Python owners because their consumer-artifact boundary has not been proven.
  This is not a complete Rust migration claim.
- Charness does not prescribe or prove a consuming repository's Git, submodule,
  worktree, or topology composition. Consumer agents own that composition and
  may use the generic reviewed-input identity capability where appropriate.
- Test/production ratios, source line counts, and broad retained-Python typing
  campaigns are not treated as consumer value without a measured JTBD.
