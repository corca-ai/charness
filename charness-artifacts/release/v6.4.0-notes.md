# charness 6.4.0

Gates that could not distinguish "checked" from "never looked" now say which, a
mutation summary stopped claiming a score it never took, and a discovery
predicate that had been quietly excluding a real validator was widened.

## A green that could not tell "checked" from "never looked"

These gates refused correctly over the population their scan admitted, without
saying what the scan never reached. Each now publishes that number in its own
output:

- `check_skill_ownership_overlap` — `scanned_files`, an `uncovered` breakdown by
  why the walk misses each class (with `excluded_build_artifacts` a key INSIDE
  `uncovered`, deliberately not summed into `uncovered.total`, and counting generated
  paths sitting at the `skills/public/` level as well as inside each skill), and a
  `did_not_judge` on every run that READ a file, including the passing one. The caveat
  previously lived only inside the stale-waiver advisory, which is emitted
  conditionally, so a clean run said nothing about partial coverage. Any run that
  READ NO FILE — `skills/public/` absent, present but holding no skill directory, or
  holding only directories with nothing readable in them — publishes no `did_not_judge`
  at all. `scanned_files: 0` is the discriminator, and the withhold itself is the
  signal that nothing was judged. **It withholds the gap list, not the gap count.** A
  run that walked and read nothing still publishes the real `uncovered` numbers beside
  `scanned_files: 0` — nothing was read, and here is how much was there to miss. An
  all-empty `uncovered` is not a discriminator for anything: a genuinely empty tree
  reports one because that is the measurement, and so does an absent root. Read
  `scanned_files: 0` for "nothing was read" and read `uncovered` as the measurement it
  is. Do not build a reader that discards `uncovered` on a `scanned_files: 0` run;
  that recreates the under-claim on the reading side.
- `check_dup_ratchet` — `scope_paths`, `scope_coverage`, and a `did_not_judge`
  naming how many tracked files sit outside the scanned scope. Its human `SCOPE:`
  line is keyed on whether the CODE SCAN produced a result, not on the whole-gate
  degrade flag: the scan runs before any degrade cause can short-circuit, so a
  missing overlay or an unreadable baseline still forms families and still has a
  true scope to report. A failed code scan replaces the line rather than removing it —
  the payload still carries a `SCOPE:` message, saying the scan produced no result — so
  do not grep for the absence of `SCOPE:` as the discriminator. That run
  adds an explicit `did_not_judge` entry saying the in-scope files went unjudged
  too — without it the payload names a gap scoped entirely to files OUTSIDE the
  scope, which reads as "everything inside was judged".
- `check_docs_graph` — `link_only_lines_slack`, the room a monotone ratchet
  silently tolerates when the measured count falls below the recorded bar.
- `check_runtime_budget_universe` — `checked`, `universe_size`,
  `universe_sources`, `second_direction_status`,
  `malformed_budget_profile_blocks`, and `unreachable_by_selected_profile`.

Those fields are additive: none of them changes what a gate refuses, and no exit code
moves because of them.

**One refusal in this release did change, in the same gate.**
`check_skill_ownership_overlap`'s allowlist parser now requires the `<reason>` field
that the format line, `.agents/surfaces.json`, and the installed
`create-skill/references/portable-authoring.md` all already declared required — it had
been accepting an entry that stopped at the owner id, so the field that makes a waiver
reviewable was optional in fact. A reasonless waiver is now dropped rather than
honoured, so the mention it was silencing returns as a violation and that repo goes
from exit 0 to exit 2. The gate also publishes `malformed_allowlist_lines`, because a
dropped waiver whose overlap is already gone reaches no other field: no finding, no
stale row, only a quietly smaller `allowlist_size`. The literal `<reason>` placeholder
the gate suggests in its own remediation string is rejected too.

**Read this before you expect to see these numbers. None of them reliably reach an
operator who just runs the gate lane.** `check_skill_ownership_overlap` is queued by
nothing in `scripts/run-quality.sh`, so its numbers never appear on that lane. They
are not manual-only, though: the gate is listed in the skill-package surface's
`verify_commands`, so
a slice closeout touching a skill does run it. The other gates are queued, but that
runner surfaces a PASSING check's
log only when the log carries an attention marker (`WARNING`, `WARN`, `WEAK`,
`ADVISORY`) — and `check_docs_graph` emits no marker on any path, while
`check_runtime_budget_universe` marks only the not-armed, malformed-block, and
unbudgeted-command cases. An armed, clean runtime-budget run and every green
docs-graph run are suppressed exactly as the dup ratchet's `SCOPE:` line is.
`--review` sets `RUN_QUALITY_VERBOSE` and shows them; `--release` does not.

An earlier draft of this paragraph said the docs-graph and runtime-budget numbers DO
reach that operator. They do not, and the sentence contradicted the list above it,
which names `unreachable_by_selected_profile` as a runtime-budget field. Being wrong
in the operator's favour, inside the paragraph whose only job is to disclose the
limitation, is the failure this release is about. A number nobody reads is not a
signal; tracked as issue #703 rather than papered over here.

What the runtime-budget gate still does NOT count is stated rather than invented:
whether a budgeted label the runner names ever RUNS. That is the open half of
issue #546, it needs operator intent the gate does not hold, and `did_not_judge`
says so on every armed verdict.

## `UNMEASURED`: a mutation summary that scored nothing no longer reports FAIL

`FAIL` is the verdict of a run that measured and lost. A run that scored no
mutants was reporting the same word, so scheduled aborts published for days as
mutation-score regressions. These routes reach the state, and each now reports
`UNMEASURED`:

- the coverage baseline aborted before mutation ran,
- the StrykerJS report is missing,
- the denominator is empty (`killed + survived == 0`), which also covers the
  timed-out and pending arms — a run that timed out or ended pending with nothing
  scored now reports `UNMEASURED`. It previously reported `FAIL-incomplete` on the
  pending arm always, and on the timed-out arm only when completion was short; a
  timed-out run above the completion floor reported a plain `FAIL`. Either way the
  word claimed a measurement that never happened.

**Exit codes are unchanged.** An unmeasured surface is still a red workflow; only
the word changed.

**Read this if you grep the summary.** An external check doing
`grep -q 'Status: \*\*FAIL\*\*'` on a baseline abort now finds nothing and goes
green. The exit code is the contract and it did not move, and this surface is
documented as dogfood-only rather than a portable consumer requirement — but if
you built on the token, this is the release that changes it.

## The discovery predicate was positional, and it was excluding a real validator

`check_consumer_validator_catalog` admitted a packaged module only if its basename
STARTED with `check_` or `validate_`. `issue_validate_closeout_draft.py` carries
the token in the middle, so it was never discovered, needed no catalog decision,
and nothing said so. The predicate is now position-independent over the same
tokens.

The token pair was deliberately not widened — `audit`, `guard`, `lint`, `verify`
each look like the next reasonable entry and each would be a longer list rather
than a better rule. The checker instead reports `candidate_predicate`,
`packaged_module_count`, `scanner_excluded_count`, and `uncovered_module_count`,
so its green no longer reads as coverage of the whole package.

**Read this if you vendor or pin the catalog.** `candidate_patterns` in
`consumer-validator-catalog.yaml` must equal the checker's own tuple exactly, and
a mismatch is a hard `CatalogError` rather than a warning. A pinned `6.3.0`
catalog against a `6.4.0` checker will refuse. Ship them together.

No consumer adoption file needs an edit: every `consumer_facing: true` entry was
already discoverable under the old predicate, and the one newly admitted module is
decided `consumer_facing: false`.

## Consumer-visible surface

These files install into consuming repos through the `quality` skill:
`check_dup_ratchet.py`, `dup_ratchet_lib.py`, `dup_ratchet_git.py`, and
`runtime_profile_lib.py`. Their payloads gained keys; none was removed and no
meaning changed. `runtime_profile_lib.malformed_budget_profile_blocks` is newly
exported.

**References install too, and these changed.** `packaging/charness.json`
exports `skills/public` wholesale, so a skill's `references/` travels with its scripts:

- `quality/references/dup-ratchet.md` — the key contract was rewritten. Its previous
  discriminator said a published `scope_paths` meant the files had been judged. That
  is false when the code scan produced no result, and the section now names the
  `did_not_judge` entries that discriminate — in ONE direction only. Their presence
  tells you the in-scope files were not judged; their absence does not tell you they
  were. **If you built a reader on the
  old rule, this is the paragraph to re-read.**
- `quality/references/mutation-testing.md` — teaches `UNMEASURED`, which is half the
  reason this is a minor rather than a patch.
- `quality/references/consumer-validator-catalog.yaml` — the `candidate_patterns`
  change described above.

`release/scripts/plan_release_run.py` changed too, through the `release` skill: it now
declares its own CLI timeout budget instead of inheriting the shared script default,
moving its wall-clock kill boundary from 10s to 90s. It is a report-only planner, so
nothing it decides changed — but the boundary at which it gives up did, and
`CHARNESS_SCRIPT_TIMEOUT_SECONDS` still overrides it. The old budget sat close enough
to the planner's own runtime that any parallel load could kill it mid-report; that is
issue #707.

The repo's own `scripts/` tree ships inside the plugin too, and modules there changed.
They are not listed above, and the reason is a RULE rather than a list, because a list
here would rot the way the ones this release removed did:

> A packaged module is discovered only if its basename carries `check_` or
> `validate_`. A discovered one has a catalog decision. **An undiscovered one has no
> decision in either direction** — it ships, and it sits in `uncovered_module_count`,
> unless it is a scanner exclusion, which IS a decision and which the checker counts
> separately as `scanner_excluded_count`.

The scan boundary is owned by the **checker**, not by the catalog: `scanner_exclusions`
in the YAML must restate the checker's own tuple exactly, and a mismatch is a hard
`CatalogError`. Adding a YAML entry does not move a module out of
`uncovered_module_count` — it gets you a refusal. Letting the data file narrow its own
candidate set would recreate the under-enumeration this gate exists to prevent.

The exclusion arm exists because putting the most explicitly considered module into a
bucket labelled "never looked at" would be the same defect this release removes. An
earlier draft of this rule omitted that arm.

The changed `scripts/` modules that carry a token are decided `consumer_facing: false`
— maintenance gates, not a consumer-authored contract — except the checker itself,
which is the scanner and is named under `scanner_exclusions` with a reason instead. The
tokenless ones are undecided, and this release both added to that population and left
it larger than any earlier draft of this paragraph admitted. Run
`check_consumer_validator_catalog.py` for today's membership rather than trusting a
count written here.

One of them is worth naming because it is new and because packaged modules now
import it: **`waiver_file_lines.py`**, one function shared by the waiver-file parsers
that had converged on the same line-iteration idiom. `check_skill_ownership_overlap.py`
imports it with a fallback; `claim_fidelity_lib.py` and `boundary_bypass_ratchet_lib.py`
import it bare. **If you vendor individual packaged scripts rather than the whole
plugin, the bare importers now need this module beside them.**

`check_skill_ownership_overlap.py` is decided `consumer_facing: false`. The others
carry no token, so the catalog decides nothing about them either way — they are the
undecided bucket the rule above names. No `consumer_facing: true` entry names any of
them, so no wired consumer contract breaks; that follows from the catalog's
consumer-facing set, not from a decision on these modules. A hand-copied script that
worked at `6.3.0` will still fail to import at `6.4.0`.

Costs worth knowing: the dup ratchet now runs a `git ls-files` on every armed evaluate
run — not on every invocation; the inert, adapter-invalid, and re-baseline paths return
before it, and inert is where a consuming repo starts. And `check_docs_graph`'s
`link_only_lines_slack` is typed integer-or-string, returning a sentence on the
path where slack is not computable.

## Not claimed

- The scheduled `Mutation Tests` workflow has **not** been observed producing a
  verdict since the repair that unblocked it. That lane has no push trigger, so
  nothing about this release's commits started it. It does carry
  `workflow_dispatch`, and a dispatch runs in `full` mode, so a verdict was
  obtainable on demand and was not taken — say "we did not dispatch it", not "it
  could not be observed". A dispatch verdict is also the weaker one: only a
  `schedule` run computes `base_sha` and can post the recovery candidate. What IS
  observed is the standing suite completing green on
  CI (`11197 passed` in 18m35s) on the run that previously failed with the
  `test_command_plan_preflight.py` failures — that is evidence for the cause repair, not for the
  mutation lane itself.
- A second, uncharacterized mutation failure mode from the `2026-08-19` and
  `2026-08-20` scheduled runs remains live. The repair in this release is necessary for a verdict, not proven
  sufficient.
