# SUMMARY
The repo already carries commands in at least five structurally incompatible shapes, none of which currently produce a parsed invokes-edge graph. `.agents/surfaces.json` stores `sync_commands`/`verify_commands` as flat opaque strings (sometimes full shell scripts with for-loops, subshells, `trap`, and `mktemp`), consumed only by string-level tooling (`repograph match-surfaces`, `scripts/staged_commit_gate_plan.py`, `select_verifiers`-style closeout logic) that flattens/dedupes them but never tokenizes argv. `scripts/run-quality.sh` carries commands as literal bash argv sequences passed positionally to `queue_selected "label" <argv...>`, with a hard convention (enforced by `assert_label_in_universe`, itself fed by a self-admittedly fragile regex reader `quality_label_universe.py`) that gate labels must be double-quoted literals because the label/verbosity/budget readers parse this file as text, not as executed bash. Git hooks (`.githooks/pre-commit`, `pre-push`, `commit-msg`) inline direct `python3 scripts/x.py` invocations and also re-invoke `./scripts/run-quality.sh` with computed label subsets. CI carries commands two ways: `.github/workflows/quality-core.yml` inlines one shell command per `run:` step (a static mirror of a `run-quality.sh` subset, checked by `check_command_dominance`/`inventory_ci_local_gate_parity`), while `.github/workflows/mutation-tests.yml` resolves its actual commands indirectly from `.agents/quality-adapter.yaml`'s `mutation_testing.commands.{dry_run,full,sample,summary}` string fields via `yq`, then executes them through a GitHub Actions expression (`run: ${{ steps.adapter.outputs.cmd_full }}`) — a two-hop, cross-file carrier with `&&`-chained sub-commands and a `--test-command '<nested full command string>'` argument that is itself a command carrier. `package.json` scripts are single command strings under `npm run <name>`. `command_plan_preflight.py` defines the one already-structured carrier: JSON `{schema_version, targets:[{id,query,expected_path}], refs:[{id,ref}], commands:[{id, owner_target, argv:[...], help_argv:[...]}]}` with an explicit `{target:<id>}` token that must appear as a standalone argv element bound one-to-one to `owner_target`, resolved against a live `rg --files` inventory (exact match, then basename, then fnmatch glob) rather than a literal path. `.agents/command-docs.yaml` adds a sixth shape: single `help_command: ./charness <subcommand> --help` strings per CLI node. The existing native crate (`native/repograph`, ABI frozen 2026-08-28) already ingests `.agents/surfaces.json` via `match-surfaces` but only flattens/dedupes its command strings — it performs zero argv or invokes parsing, so there is no native precedent to extend for #746's invokes-edge work; it has to be built new. The closest existing invokes-style extractor is `scripts/check_plugin_asset_command_carriers.py`, a narrow regex (`(python3|bash|sh) [flags]* ['"]?skills/(public|support)/....(py|sh)`) scoped only to `plugins/**/*.{json,yaml,yml}` string values, built for a kind-bearing-path check, not a general command-to-file edge.

# DETAILS

## 1. `.agents/surfaces.json` verification/sync commands

Format: JSON object with a top-level `surfaces` array; each surface has `sync_commands: [string]` and `verify_commands: [string]` (plus `generated_markdown[].generator`/`sync_command` for a paired generator/sync command). Every command is a *plain shell command string*, executed by whatever consumer runs it (not JSON argv). Examples straight from the file (`/home/hwidong/codes/charness/.agents/surfaces.json`):

- Simple invocation: `"python3 scripts/validate_packaging.py --repo-root ."`
- Local script wrapper: `"./scripts/check-docs.sh"`
- Shell control flow embedded in the string (for-loop + early exit):
  `"for evidence_file in charness-artifacts/goals/*.json; do python3 -m json.tool \"$evidence_file\" >/dev/null || exit $?; done"`
- Nested Python one-liner as a command string:
  `"python3 -c 'import json, pathlib; [json.loads(line) for path in pathlib.Path(\"charness-artifacts/goals\").glob(\"*.jsonl\") for line in path.read_text(encoding=\"utf-8\").splitlines() if line.strip()]'"`
- Multi-statement shell with `mktemp`, `trap`, and a real binary invocation (`specdown`), used identically inside `surfaces.json` and inside `run-quality.sh`'s own `specdown` gate.

Consumers named in the file's own `source_paths`: `scripts/staged_commit_gate_plan.py` and `scripts/check_consumer_validator_catalog.py`; the native `repograph match-surfaces` command (frozen ABI, `native/repograph/ABI.md`) also reads `.agents/surfaces.json` and, given a set of `--path` changed paths, returns `matched_surfaces[]` with `sync_commands`/`verify_commands` **flattened and first-occurrence-deduplicated as opaque strings** — it does not parse or tokenize them. This is the "select_verifiers"-shaped consumption path the task description refers to: match-surfaces answers "which command *strings* apply to this changed-path set," not "which files does this command invoke."

Validation of the manifest shape itself is `scripts/validate_surfaces.py` (surface `surface-obligations`), separate from validating that the commands are runnable.

## 2. `scripts/run-quality.sh`

Full file: `/home/hwidong/codes/charness/scripts/run-quality.sh` (1306 lines).

- Command carrier shape: bash **argv tokens**, not a single string — `queue_selected "<label>" <argv-word> <argv-word> ...` or the lower-level `queue_timed`. E.g.:
  - `queue_selected "validate-skills" python3 scripts/validate_skills.py --repo-root "$REPO_ROOT"`
  - `queue_selected "check-docs" ./scripts/check-docs.sh`
  - `queue_selected "pytest" env CHARNESS_STANDING_PYTEST_PYTHON=python3 python3 scripts/run_standing_pytest.py "${PYTEST_FLAGS[@]}"` — note the `env VAR=value` prefix and a bash array expansion (`"${PYTEST_FLAGS[@]}"`) whose actual contents are computed earlier from `RUN_QUALITY_MODE`/`--include-release-only` conditionals; a static reader cannot know the final argv without evaluating that bash logic.
  - Escaped, multi-line `bash -c '...'` payloads for `specdown` (embeds `mktemp -d`, `trap`, and a nested `specdown run -config ... -jobs 4 -out ...` invocation) and for `check-provenance-contract`'s fallback branch (heredoc-like multi-line script body). These are genuinely nested shell scripts, not simple argv.
- Label list structure: labels are queued via ~80 `queue_selected`/`queue_timed`/`queue_agent_browser_runtime_gate` call sites scattered through the file (lines ~940–1291). There is a companion static reader, `scripts/quality_label_universe.py`, that extracts every label this file can ever queue via a **regex over the bash source itself** (three sources: literal `queue_*` call sites excluding dispatcher-forwarded `"$label"`, the computed aggregate label `run-quality-${MODE}[-release]`, and adapter `startup_probes` with `class: standing`). That module's own docstring states plainly: *"a regex over bash is load-bearing here [only] without [runtime `assert_label_in_universe`] this module would be a guess with a confident tone."* `run-quality.sh` then asserts at queue time (`assert_label_in_universe`) that every label it queues is one the reader found, turning a silent static-extraction miss into a loud runtime failure rather than a wrong verdict later. This is the strongest existing precedent in the repo for "how much to trust a static parse of a bash command carrier," and directly informs what a typed core must do for invokes-edges from the same file.
- `UNESTABLISHED_CAPABLE_LABELS` (line 397): `"inventory-nose-clones docs-graph check-docs check-closeout-classification-parity check-export-self-sufficiency check-artifact-referents"` — a space-separated allowlist, opt-in per label. A queued command's exit code `3` (`UNESTABLISHED_EXIT`) or `4` (`PARTIAL_EXIT`) is treated as the tri-state "unestablished/unproven" verdict *only* if its label is in this list; otherwise the same exit codes are treated as `fail`. Membership is decided per-gate after that gate's own exit-code contract is read (comment: "OPT-IN PER LABEL, never a global reinterpretation of the byte" — e.g. `pytest` exits 3 on `INTERNAL_ERROR` and must never be laundered into unestablished).
- "Validation entrypoint": the literal phrase appears in `docs/host-packaging.md` line 25: `"validation entrypoint: [scripts/validate_packaging.py](../scripts/validate_packaging.py)"`, i.e. it names *the one script* that is the canonical, single-source checker for a given surface/contract (paired with an "export entrypoint" for the generator). It is a documentation convention (one line per surface naming its owning validator script), not a `run-quality.sh`-specific structure.

## 3. Git hooks / CI / package.json / Makefile

- No `Makefile` exists in the repo (only `package.json`).
- `package.json` (`/home/hwidong/codes/charness/package.json`): `scripts` object maps npm script names to single command strings, e.g. `"test:mutation:js:dry-run": "python3 scripts/run_js_mutation.py --repo-root . --mode dry-run"`.
- `.githooks/pre-commit`: inline `python3 -B scripts/check_git_identity.py --repo-root "$REPO_ROOT"` plus a mutation-recovery guard invoking `python3 scripts/mutate_and_restore.py --repo-root . --check-recovery` (named only in an error message, not executed).
- `.githooks/pre-push`: inline `python3 scripts/prepush_close_keyword_guard.py --repo-root "$REPO_ROOT" --remote "${1:-origin}"`, `python3 scripts/classify_push_diff.py --paths-stdin --repo-root "$REPO_ROOT"`, and then re-invokes the run-quality carrier itself either narrowed (`CHARNESS_QUALITY_LABELS="$DOCS_ONLY_LABELS" ./scripts/run-quality.sh --read-only`) or broad (`./scripts/run-quality.sh --full --read-only`) — i.e. one carrier (a hook) dynamically selects a subset of another carrier's labels via an environment variable containing a comma-separated label list.
- `.githooks/commit-msg`: inline `python3 scripts/check_issue_closeout_commit_msg.py --repo-root "$REPO_ROOT" --commit-msg-file "$1"`.
- `.github/workflows/quality-core.yml`: one shell command string per `run:` step, each invoking a repo-owned validator directly (e.g. `run: python3 scripts/validate_packaging.py --repo-root .`, `run: ./scripts/check-markdown.sh`). Explicitly documented as a static, hand-authored mirror of a `run-quality.sh` subset (`# charness:gate-policy local-gate-subset-mirror`), policed by `scripts/check_command_dominance.py` and `skills/public/quality/scripts/inventory_ci_local_gate_parity.py` for drift.
- `.github/workflows/mutation-tests.yml`: commands are **not** written in the workflow file. A step reads `.agents/quality-adapter.yaml` via `yq` into `steps.adapter.outputs.cmd_{dry_run,full,sample,summary}`, then a later step runs `${{ steps.adapter.outputs.cmd_full }}` (a GitHub Actions expression substitution) — a two-hop carrier: workflow YAML step → adapter YAML field → literal command string, only resolvable by reading both files together. The adapter's own command strings chain sub-invocations with `&&` (`"python3 scripts/run_cosmic_ray_mutation.py --repo-root . --mode dry-run && npm run test:mutation:js:dry-run"`) and one field nests a *complete second command string* inside a flag value consumed by the outer script, not by the shell: `"python3 scripts/sample_mutation_files.py --repo-root . --test-command 'python3 scripts/run_standing_pytest.py --repo-root .'"`.

## 4. `scripts/command_plan_preflight.py` and the `{target:<id>}` grammar

File: `/home/hwidong/codes/charness/scripts/command_plan_preflight.py`; grammar documented at `docs/parallel-execution.md` lines 72–87 and pinned by `tests/quality_gates/test_command_plan_preflight.py`.

- This is the one carrier in the repo that is already **structured JSON argv**, not a shell string: a plan is `{"schema_version": 1, "targets": [...], "refs": [...], "commands": [...]}`.
- `targets[]`: `{"id": str, "query": str, "expected_path"?: str}`. Resolution runs `rg --files --hidden --glob '!.git/**'` from `--repo-root`, then matches `query` by exact repo-relative path, else by basename (`Path(path).name == query`) if `query` has no `/`, else by `fnmatch.fnmatch(path, query)`. Zero matches, ambiguous (>1) matches, or an `expected_path` not present among matches are hard refusals (`target-not-found`/`target-ambiguous`/`target-mismatch`) — never a guessed sibling.
- `refs[]`: `{"id": str, "ref": str}`, verified with `git rev-parse --verify --quiet "<ref>^{commit}"`.
- `commands[]`: `{"id": str, "owner_target": str, "argv": [str,...], "help_argv"?: [str,...]}`. The `{target:<id>}` token (`_expand_token`) must appear **as a standalone argv entry** (`_standalone_target_token_errors`); an embedded form like `--input={target:demo}` is a refusal, not a substitution. `_validate_owner_binding` requires `argv` to contain *exactly* `{target:owner_target}` and, if `help_argv` is given, the same single token — binding the command's help probe to the same resolved path so a healthy-but-wrong-owner `--help` can't produce a false green. If `help_argv` is omitted it's derived (`_derived_help_argv`): insert `--help` right before the first flag-looking token, else append it. The checker then runs only `<help_argv> --help`-style probes (never the real `argv`) and diffs `_planned_flags(argv)` (anything starting with `-`) against flags accepted by the target's `--help` output (via `argparse_surface_lib`), refusing on any planned flag the parser doesn't advertise.
- Scope note from `docs/parallel-execution.md`: this plan format is for a "manually assembled fan-out whose target, ref, or flag resolution is otherwise ambiguous," explicitly *not* a replacement for `charness task run`'s own base/branch/worktree preflight, and it "proves resolution and parser ownership only, not runtime, installed state, hosted state, or external truth."

## 5. How a command string references files, and what's currently unparseable

Argv-embedding patterns actually present in the repo:
- Direct: `python3 scripts/<name>.py [--flag value]...` / `./scripts/<name>.sh` — trivially tokenizable (first non-flag word after the interpreter is the invoked file).
- Env-prefixed: `env VAR=value python3 scripts/x.py ...` (run-quality.sh) — the invoked-file token shifts past `env` and any `KEY=VALUE` tokens.
- Package-qualified module invocation: `python3 -m pytest -q tests/...`, `python3 -m py_compile <glob-expanded files>` — the "file" here is a module name or a shell-glob-expanded array, not a literal path; `-m` targets are not filesystem paths at all.
- Chained: `"<cmd1> && <cmd2>"` (quality-adapter.yaml `mutation_testing.commands.dry_run`/`full`) — requires splitting on shell control operators (`&&`, `||`, `;`, `|`) to find multiple invoked commands in one string.
- Nested-in-argument: `--test-command 'python3 scripts/run_standing_pytest.py --repo-root .'` — a full second command string living inside a single-quoted flag *value*; whether to recurse into it is a real design decision (the outer script, not the shell, is what dispatches it).
- Shell-script-as-string: `for x in <glob>; do python3 -m json.tool "$x" ... ; done` (surfaces.json), and full `bash -c '<mktemp/trap/multi-statement script>'` blocks (run-quality.sh's `specdown` and `check-provenance-contract` fallback) — genuinely require a shell grammar (loops, subshells, `trap`, variable expansion) to extract the invoked commands safely; a token-scan/regex will either miss invocations or hallucinate false ones.
- Variable/array indirection: `"${PYTEST_FLAGS[@]}"`, `"$RUN_QUALITY_LABELS"` — the literal command string in the source file does not contain the runtime argv; extraction can only capture the static prefix and must mark the rest unresolved rather than guess.
- Two-hop / cross-file indirection: `run: ${{ steps.adapter.outputs.cmd_full }}` in `mutation-tests.yml` names no command in the file that contains the "invocation site" at all; the actual command string lives in `.agents/quality-adapter.yaml`.
- Target-token indirection: `command_plan_preflight.py`'s `{target:<id>}` requires resolving against a separately-declared, `rg`-inventory-checked `targets[]` array before any file reference is known.

Currently unparseable/out of scope for any existing repo tooling: nested `bash -c` multi-statement scripts with `trap`/`mktemp`/loops; `&&`/`;`-chained multi-command strings; commands nested inside another command's flag value; bash-array/variable-expanded argv in `run-quality.sh`; and the two-hop GitHub Actions ↔ adapter-YAML indirection in `mutation-tests.yml`. The only existing regex-based command-carrier extractor, `scripts/check_plugin_asset_command_carriers.py`, is deliberately narrow: it walks all string leaves of `plugins/**/*.{json,yaml,yml}` and matches only `(python3|bash|sh) [-flag[=val]]* ['"]?(skills/(public|support)/....(py|sh))` to catch authoring-layout paths that survived into the shipped export — it does not touch `.sh` script bodies, does not touch the authoring-tree `.agents/surfaces.json` itself, and explicitly is not a general invokes-edge extractor. `repograph match-surfaces` (native, ABI-frozen) is the only native precedent that reads `.agents/surfaces.json`'s commands at all, and it only flattens/dedupes the strings — zero argv or file-reference parsing.

<design_constraints>
- The core needs to model at least five structurally distinct command-carrier shapes as first-class node/edge kinds, not one generic "command string" type: (1) opaque shell-string carriers (surfaces.json sync/verify commands, quality-adapter.yaml mutation commands, package.json scripts, .githooks inline calls, command-docs.yaml help_command); (2) bash-argv-token carriers where the file's own text is the parse target (run-quality.sh queue_* call sites), which the repo already treats as fragile-and-load-bearing only under a runtime self-check (assert_label_in_universe) — a static invokes-edge here should likely be marked advisory/unestablished-capable rather than authoritative unless a matching runtime assertion exists; (3) structured JSON argv-with-indirection carriers (command_plan_preflight.py plans, using `{target:<id>}` tokens resolved against a live rg inventory, not literal paths); (4) two-hop cross-file carriers where the invocation site (GH Actions `run: ${{ steps.X.outputs.Y }}`) and the command text (quality-adapter.yaml) live in different files and must be joined; (5) CLI-subcommand-tree carriers (.agents/command-registry.json, command-docs.yaml) that are not shell invocations at all but a static path/group taxonomy of the `charness` binary itself.
- Command strings routinely contain shell control flow (&&, ||, ;, |, for-loops, subshells, trap, mktemp) that a naive "first two argv tokens" heuristic will misparse; the extractor must either implement/embed a real (bounded) shell-splitting pass or explicitly refuse/flag such strings as unparseable rather than silently emitting a wrong or partial invokes-edge.
- Some carriers nest a full second command string inside a flag value consumed by the outer program, not by the shell (mutation-tests' `--test-command '...'`); the design must decide, per carrier kind, whether nested command strings recurse into further invokes-edges or terminate as an opaque argument.
- Some carriers are irreducibly dynamic at static-parse time: env-prefixed commands (`env VAR=value ...`), bash array/variable expansions (`"${PYTEST_FLAGS[@]}"`), and the mutation-tests.yml adapter-output indirection resolve to a final argv only at runtime; the schema needs an explicit "unresolved/dynamic" tail marker distinct from a resolved file reference, mirroring the ABI's existing `unestablished` object convention (path/status/detail) and its ordinal exit-code discipline (0 clean, 1 findings, 2 usage error, 3 unestablished/inventory-failure, 70 internal failure) documented in native/repograph/ABI.md.
- `{target:<id>}` token resolution is not path-literal-lookup; it goes through the same `rg --files` inventory-based query matching (exact → basename → fnmatch) used by command_plan_preflight.py, including the exact ambiguous/not-found refusal semantics — any invokes-edge builder that wants to resolve these tokens must reuse or reimplement that exact resolution algorithm to stay consistent with the already-frozen preflight tool, not invent a second one.
- The existing repo convention for "is this string actually a command carrier worth extracting" is narrow and purpose-built (check_plugin_asset_command_carriers.py's regex is scoped to plugins/**/*.{json,yaml,yml} and to skills/(public|support)/*.py|sh targets specifically for the authoring/export-layout drift question); the #746 design must not silently widen that existing gate's scope, and should treat its regex as a template for "how narrow and single-purpose a static command-carrier scanner already has to be to stay trustworthy in this repo," not as reusable infrastructure.
- No native precedent currently performs invokes-edge extraction; `repograph match-surfaces` only flattens/dedupes surfaces.json's command strings, so #746 is greenfield work for this specific capability, not an extension of an existing typed pass.
- Whatever static bash/text parsing the new core adds over run-quality.sh (or any other bash carrier) should either be paired with a runtime cross-check analogous to `assert_label_in_universe`, or its output should be explicitly reported as advisory/unestablished per the "gate label reader" pattern already established by scripts/quality_label_universe.py — trusting a bare regex-over-bash parse as ground truth repeats a mistake this repo has already identified and mitigated once.
</design_constraints>
