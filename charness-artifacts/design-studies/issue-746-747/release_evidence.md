# SUMMARY
Charness has no explicit OS/arch support matrix; the only proven tuple is Linux x86_64 via GitHub Actions ubuntu-latest CI (quality-core.yml:38, mutation-tests.yml:35). The install path (init.sh) is bash-only and POSIX-$HOME-dependent, which covers Linux, macOS, and WSL but not native Windows; scripts/bootstrap_runtime.py has Windows-aware branches (os.name == "nt") that are never exercised in CI. The closest real precedent for a platform-support declaration is integrations/tools/*.json's OS-only "platforms" enum {linux, macos, windows, any} (schema at integrations/tools/manifest.schema.json:50-60), used for external Rust/Go binary tools like nose, gitleaks, tokei — none of which is exercised with per-arch (x86_64/arm64) distinction anywhere in the repo. Releases today are entirely git/GitHub-native: bump packaging/charness.json's single version field (source of truth), sync it into checked-in plugin manifests, tag `vX.Y.Z`, push, then `gh release create --verify-tag --notes-file <release-notes.md>` — no binary artifacts, checksums, or cargo-dist are involved anywhere in the pipeline, and there is no .github/workflows/release.yml (release is agent-run from a maintainer machine, not CI). native/repograph (the #745 spike crate) is completely unwired from packaging/charness.json, the release skill, and any CI workflow — it is source-only, non-production, built locally via `cargo build --release --offline`, pinned to rust-toolchain.toml 1.96.0. cargo-dist 0.32.0 is present on the host PATH (~/.cargo/bin) but has zero repo configuration (no dist-workspace.toml, no [workspace.metadata.dist] block). The repo does already use sha256 as an internal integrity primitive (scripts/sync_root_plugin_manifests.py per-file digest snapshotting; skills/public/release/scripts/release_delta.py path_list_sha256; release_tag_identity.py binding a tag to a full lowercase git object id) — this is the cheapest existing idiom to extend for "reproducible artifact identity," rather than adopting a binary-registry-style checksum manifest that has no repo precedent.

# DETAILS

## 1. Existing OS/arch support evidence

- **No explicit supported-tuple doc exists.** `docs/operator-acceptance.md`, `docs/readme-proof.md`, and `README.md` contain zero mentions of macOS/Linux/Windows/WSL/x86_64/aarch64 (verified by repo-wide grep). There is no host-matrix table anywhere in `docs/`.
- **CI-proven tuple: Linux only (ubuntu-latest / x86_64).** `.github/workflows/quality-core.yml:38` and `.github/workflows/mutation-tests.yml:35` both pin `runs-on: ubuntu-latest`. No macOS or Windows runner exists in the two GitHub Actions workflows in the repo (`.github/workflows/` contains exactly these two files).
- **Install path evidence (`init.sh`):** `init.sh:1` shebang is `#!/usr/bin/env bash`; `init.sh:5` requires `HOME_ROOT="${HOME:?HOME must be set}"` (POSIX `$HOME`). README.md's Quick Start (`curl -fsSLo ... | bash /tmp/charness-init.sh`) presupposes a POSIX shell with `curl` and `bash` — this covers Linux, macOS, and WSL, but there is no native Windows (cmd/PowerShell) invocation path documented or tested.
- **Code-level Windows-awareness without proof:** `scripts/bootstrap_runtime.py:93` (`python_in_runtime`) and `scripts/bootstrap_runtime.py:202` (`write_launcher`) both branch on `os.name == "nt"` to produce Windows venv layouts (`Scripts/python.cmd`) and a `.cmd` launcher — but this code path is never exercised by CI (ubuntu-latest only) and never referenced by any doc as a supported target.
- **The closest real "platform support" declaration in the repo is OS-only, per external tool, not per-charness-binary.** `integrations/tools/manifest.schema.json:50-60` defines a `platforms` enum of exactly `["linux", "macos", "windows", "any"]` — no CPU architecture dimension exists anywhere in this schema or its consumers. Concrete declarations:
  - `integrations/tools/nose.json:9-12` → `["linux", "macos"]` (a Rust CLI, released via `curl ... nose-cli-installer.sh | sh` and optional `brew install corca-ai/tap/nose` — see `nose.json` lifecycle.install.commands and notes)
  - `integrations/tools/gitleaks.json`, `agent-browser.json`, `glow.json`, `specdown.json` → `["linux", "macos"]`
  - `integrations/tools/tokei.json`, `ruff.json`, `lychee.json`, `vulture.json`, `awiki.json` → `["linux", "macos", "windows"]`
  - `integrations/tools/defuddle.json`, `github-gh.json` → `["any"]`
- **Conclusion for #747 design:** the only thing that can honestly be called "current supported tuples from existing install evidence" is: CI-proven = Linux (ubuntu-latest, x86_64 GitHub-hosted runner); install-script-reachable = Linux/macOS/WSL (bash + curl + python3, per `init.sh`); code-aware-but-unproven = native Windows (bootstrap_runtime.py `nt` branches). No arch (x86_64 vs aarch64) distinction is tracked anywhere. The acceptance instruction to "not expand the matrix" means #747 should describe exactly this asymmetric, partly-unproven state — not invent a claimed 6-tuple (linux/macos/windows × x86_64/arm64) matrix that has no supporting evidence.

## 2. Release process today

- **Version source of truth:** `packaging/charness.json:5` (`"version": "8.0.0"`) is the single authoritative version field. It is duplicated into `packaging/charness.json:26` (`claude.manifest.version`) and `:69` (`codex.manifest.version`) by the same file (hand-authored in the manifest itself, then propagated on bump).
- **Version bump script:** `skills/public/release/scripts/bump_version.py:53` `write_packaging_version()` reads `packaging/charness.json`, sets `data["version"]`, `data["claude"]["manifest"]["version"]`, and `data["codex"]["manifest"]["version"]`, then re-writes the file. `bump_version.py:34` `VERSION_RE` enforces strict SemVer (`major.minor.patch[-prerelease]`).
- **Sync to generated plugin manifests:** `scripts/sync_root_plugin_manifests.py` regenerates the checked-in plugin export tree (`plugins/charness/.claude-plugin/plugin.json`, `plugins/charness/.codex-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `.agents/plugins/marketplace.json`) from `packaging/charness.json` via `scripts/packaging_lib.py:227` `export_plugin_tree()` and `:370` `expected_root_artifacts()`. Verified current values: `plugins/charness/.claude-plugin/plugin.json` and `plugins/charness/.codex-plugin/plugin.json` both show `"version": "8.0.0"`, matching `.claude-plugin/marketplace.json`'s `metadata.version` and `plugins[0].version`, both `"8.0.0"`.
- **Publication mechanism — git tag + GitHub Release, no binaries:**
  - `skills/public/release/scripts/publish_release_execute.py:255` → `cli.run(["git", "tag", tag_name], cwd=repo_root)`
  - `skills/public/release/scripts/publish_release_execute.py:256` → `cli.run(["git", "push", args.remote, branch, tag_name], cwd=repo_root)`
  - `skills/public/release/scripts/publish_release_helpers.py:186-195` `create_release()` runs `gh release create {tag} --verify-tag --title {title} --notes-file <notes>` (or `--generate-notes` if no notes file) — this is the entire publish command; no `--attach`/upload of build artifacts occurs anywhere in this codepath.
  - `skills/public/release/scripts/publish_release_helpers.py:198-205` `expected_github_release_url()` derives the readback URL as `<repo_url>/releases/tag/<tag_name>` via `gh repo view --json url`, used for post-publish verification (`gh release view` plus an independent URL-fetch channel per `publish_release_post_create.py:232-395`).
  - `.agents/release-adapter.yaml`: `sync_command: python3 scripts/sync_root_plugin_manifests.py --repo-root .`, `quality_command: ./scripts/run-quality.sh --release`, `post_publish_install_refresh: charness update`, `post_publish_version_readback: charness version`, `post_publish_doctor_readback: charness doctor`.
- **No CI-driven release.** There is no `.github/workflows/release.yml`. Both existing workflows (`quality-core.yml`, `mutation-tests.yml`) are PR/push/scheduled *gates*, not publishers. `.agents/release-adapter.yaml`'s `real_host_checklist` explicitly says the maintainer must run `charness update`/`charness doctor` "on THIS maintainer/dev machine" after publish — release is an agent-run, host-executed workflow (`skills/public/release/SKILL.md` + its scripts), not an automated CI job.
- **Latest release identity (v8.0.0):** `charness-artifacts/release/2026-08-28-v8.0.0-notes.md` is the drafted/published notes body passed to `--notes-file`. It embeds a machine-generated, gate-verified "Derived claim surfaces" block (`<!-- charness:derived-claims:begin -->` … `:end`) listing scanned claim surfaces (subcommand list, skill list, shell-gate list) re-derived from the shipped tree at publish time and diffed against hand-edits — this is the repo's existing pattern for binding release-notes claims to verifiable tree state, but it operates on source-tree inventories, not build artifacts.
- **Release-identity binding uses full git object IDs, not build hashes:** `skills/public/release/scripts/release_tag_identity.py:8` `single_remote_object_id()` resolves and validates a tag's remote full 40/64-hex-char object id via a strict regex (`FULL_OBJECT_ID_RE`), refusing short SHAs or ambiguous multi-line `ls-remote` output.

## 3. Host tooling for native artifact builds

- **cargo-dist is present on the operating host but entirely unconfigured in the repo.** `~/.cargo/bin/cargo-dist` and `~/.cargo/bin/dist` both resolve, `cargo dist --version` → `cargo-dist 0.32.0`. Repo search found no `dist-workspace.toml` anywhere, and `native/repograph/Cargo.toml` has no `[workspace]` table and no `[workspace.metadata.dist]` section — it's a single non-workspace crate (`Cargo.toml:1-16`).
- **Current native build path is purely local/manual:** `native/repograph/README.md` "Build" section: `cargo build --release --offline` from `native/repograph`, pinned by `native/repograph/rust-toolchain.toml:2` (`channel = "1.96.0"`). No cross-compilation, no target triples, no release-binary distribution step exists anywhere for this crate.
- **repograph is fully isolated from the release/packaging surface today.** `packaging/charness.json`, every `.agents/*.yaml` adapter, and `skills/public/release/references/*.md` contain zero mentions of `repograph` (verified by grep). `native/repograph/README.md` states: "Non-production spike crate for issue #745 ... no gate, hook, skill, or export may depend on it." `ABI.md`'s freeze section reiterates: "The crate remains non-production until issue #746 promotes it."
- **Cheapest "reproducible artifacts with checksums" framing given this repo publishes via git, not a binary registry:** the repo already has two working sha256 idioms to extend rather than inventing a new binary-artifact-checksum pipeline:
  1. `scripts/sync_root_plugin_manifests.py:25` `_digest()` (per-file `hashlib.sha256(path.read_bytes()).hexdigest()`) and `:29` `_snapshot()` — used today to detect drift between the packaging manifest and the generated/checked-in plugin export tree (added/changed/removed/unchanged path sets).
  2. `skills/public/release/scripts/release_delta.py:32` `path_list_sha256()` — hashes an ordered NUL-joined path list to fingerprint a changed-file set for a release.
  3. `release_tag_identity.py:8` binds a release to an immutable, remote-verified full git object ID rather than a build-output hash.
  Since Charness ships source (skills, scripts, packaging JSON) through git tags + `gh release`, not compiled binaries through a registry, the cheapest reproducible-artifact story is: (a) pin `native/repograph`'s toolchain and dependency versions exactly (already done via `rust-toolchain.toml` + `=`-pinned `Cargo.toml` deps, confirmed at `native/repograph/Cargo.toml:12-16`), (b) if/when #747 needs a distributed `repograph` binary, extend the existing `integrations/tools/*.json` manifest pattern (OS-only `platforms` enum, `lifecycle.install.commands` pointing at a `curl ... | sh` installer plus optional Homebrew tap, `checks.detect` running `<tool> --version`) exactly as `nose.json` already does for a comparable Rust CLI, and (c) attach a sha256 checksum file to the GitHub Release using the same `hashlib.sha256` idiom already used by `sync_root_plugin_manifests.py`/`release_delta.py`, verified via the existing dual-channel readback pattern (`gh release view` plus an independent URL fetch) already implemented in `publish_release_post_create.py`. There is currently **no checksum verification of any kind** for the nine existing `external_binary` tool installers (`integrations/tools/*.json` — grep for `sha256`/`checksum`/`verify` found nothing beyond prose "verify with `<tool> --version`" instructions), so adding real checksum verification for a `repograph` binary would be new practice, not an extension of an existing gate.

## 4. Version binding today (source ↔ plugin export ↔ CLI)

- **Single source of truth:** `packaging/charness.json`'s top-level `"version"` field (currently `"8.0.0"`), read by `charness`'s `packaging_version()` function (`charness:348-353`) which loads `packaging/{PACKAGE_ID}.json` and returns `data.get("version")` — this is what `charness version` ultimately reports.
- **Propagation on bump:** `bump_version.py:53` `write_packaging_version()` writes the same new version into three places inside one JSON file (top-level, `claude.manifest.version`, `codex.manifest.version`), then the release flow invokes the adapter's `sync_command` (`python3 scripts/sync_root_plugin_manifests.py --repo-root .`, per `.agents/release-adapter.yaml`) to regenerate the checked-in plugin export tree so the two plugin manifests and two marketplace files match.
- **Verified consistency at v8.0.0:** `packaging/charness.json` (`"8.0.0"` in 3 places) == `plugins/charness/.claude-plugin/plugin.json` (`"version": "8.0.0"`) == `plugins/charness/.codex-plugin/plugin.json` (`"version": "8.0.0"`) == `.claude-plugin/marketplace.json` (`metadata.version` and `plugins[0].version`, both `"8.0.0"`) — all four surfaces read identically, confirming the sync path is currently in sync.
- **Generated files are explicitly non-authoritative:** `docs/host-packaging.md` states plainly: "Generated host layouts are not authoritative. If an exported manifest drifts from the shared packaging manifest, regenerate the export instead of editing the host file by hand," and lists exactly which four generated files exist and what each contains.
- **`native/repograph`'s own `Cargo.toml` `version = "0.1.0"`** (`native/repograph/Cargo.toml:3`) is completely independent of and unreferenced by `packaging/charness.json` — it has never been bound to a Charness release version, since it is a non-production, non-exported crate.

## Design constraints for #747 (release evidence / artifact tooling)

1. Do not assert a supported-platform matrix broader than what's proven: CI is Linux-only (ubuntu-latest); install-script reach is Linux/macOS/WSL (bash-dependent); Windows is code-aware but untested/unproven — any #747 claim must carry these distinct evidence tiers rather than a single flat matrix.
2. If a platform-support field is added for a `repograph` release artifact, reuse the existing OS-only enum shape from `integrations/tools/manifest.schema.json:50-60` (`linux`/`macos`/`windows`/`any`) rather than inventing a new vocabulary; there is no existing arch (x86_64/aarch64) dimension anywhere in the repo to extend, so adding one is new surface, not reuse.
3. Artifact identity must bind to an immutable full git object id (the `release_tag_identity.py` pattern), not a short SHA or a mutable branch/tag name, consistent with how the release skill already verifies tags.
4. Any new checksum/reproducibility mechanism should reuse the repo's existing `hashlib.sha256` idiom (`sync_root_plugin_manifests.py`, `release_delta.py`) for consistency, since no checksum verification exists today for any of the nine external-tool installers this repo already tracks.
5. Release publication must stay git-tag + `gh release create --verify-tag --notes-file` shaped — there is no CI-driven release workflow and no existing binary-attachment step to extend; adding binary artifacts means adding a wholly new `gh release upload`/attach step, not modifying an existing one.
6. `native/repograph`'s crate version (`Cargo.toml` `0.1.0`) is currently unbound to `packaging/charness.json`'s product version; #747 must decide explicitly whether/how a promoted `repograph` binary's version tracks the Charness product release version or has independent crate versioning, since no existing binding contract covers this case.
7. Keep the crate non-production-until-promoted framing (`ABI.md`'s freeze language, `native/repograph/README.md`) intact until #747 explicitly changes it — #747 is the promotion boundary the current docs point to.
