# Repository Topology Report — inputs for #746 typed graph design

## 1. Skill structure

`skills/public/<name>/` (20 dirs: achieve, announcement, create-cli, create-skill, critique, debug, gather, handoff, hitl, hotl, ideation, impl, issue, narrative, prove, quality, release, retro, setup, spec). Each contains:
- `SKILL.md` — required identity file with YAML frontmatter `name:` + `description:` (the `description` doubles as the model-facing trigger text). This is the canonical skill identifier — e.g. `skills/public/impl/SKILL.md:1-4` has `name: impl`.
- `scripts/*.py` — executable helpers (e.g. `skills/public/debug/scripts/plan_debug_run.py`, `scaffold_debug_artifact.py`). Every skill has a `resolve_adapter.py` and `init_adapter.py` following an identical pattern.
- `references/*.md` — non-executable doctrine docs the skill's SKILL.md points into (e.g. `skills/public/debug/references/five-whys-causal-chain.md`).
- `adapter.example.yaml` — a template for the repo-local adapter (see §2).
- `handoff/` is an outlier: no `SKILL.md` found (empty frontmatter in my scan), worth checking directly if #746 needs a uniform skill node contract.

`skills/support/` holds non-public "support runtime" skills (`web-fetch`, `markdown-preview`) plus `generated/` and a `capability.schema.json` (JSON Schema, `support_runtime` kind, requires `capability_id`, `checks.detect`/`checks.healthcheck`, `access_modes` enum). Support skills are capability-gated, not directly invoked the way public skills are.

`skills/shared/` has no SKILL.md — it's a library: `scripts/` (~25 files, mostly `reviewer_*.py` machinery shared across skills) and `references/` (~19 cross-cutting doctrine docs like `adapter-bootstrap.md`, `advisory-interpretation-contract.md`). Public skills reference it by path convention (`skills/shared/references/...`, `skills/shared/scripts/...`), not by import statement — it's filesystem-path coupling, not a Python package relationship.

## 2. Adapters (`.agents/*.yaml`, `.agents/*.json`)

Two clearly distinct classes:

**Human policy / hand-authored per-skill adapters** (`<skill>-adapter.yaml`, one per skill needing repo-local config): `achieve-adapter.yaml`, `critique-adapter.yaml`, `impl-adapter.yaml`, `issue-adapter.yaml`, `narrative-adapter.yaml`, `quality-adapter.yaml`, `release-adapter.yaml`, `retro-adapter.yaml`, `setup-adapter.yaml`, `create-skill-adapter.yaml`, `worktree-adapter.yaml`, `hitl-adapter.yaml`, `markdown-preview.yaml`. Each begins `version: 1 / repo: charness / language: en` then repo-specific knobs (`output_dir`, `preset_id`, thresholds like `quality-adapter.yaml`'s `coverage_floor_policy`). `worktree-adapter.yaml` is explicitly generated by a detector then hand-edited (comments say "auto-detected... Edit the... commands below if detection picked the wrong tool").

**Mechanically-derived / registry-style JSON+YAML** (not authored per-decision, they're indexes read by one script owner): `command-registry.json` (flat list of every `charness` subcommand path+group — this is essentially the CLI command-carrier node inventory already enumerated), `command-archetypes.json` (subcommand → accepted schema id + example fixture), `command-docs.yaml` (per-command doc/help contract), `command-dominance.yaml` (comment: "Read by ONE owner, `skills/public/quality/scripts/command_dominance_lib.py`"), `cli-side-effect-probes.json` (mutating/non-mutating classification per command), `surfaces.json` (51KB — declares "surfaces" like `checked-in-plugin-export` with `source_paths`, i.e. mirror-pair source declarations), `inference-interpretation-surfaces.json`, `consumer-validator-adoption.yaml` (validator catalog with `wired: true`/`opt_out_reason` per entry).

`.agents/plugins/marketplace.json` declares the installable plugin (`source: local, path: ./plugins/charness`). `.agents/codex-host.md` is prose (host/lane notes referenced from root CLAUDE.md).

**Design implication:** adapters aren't one node type — some are per-skill config (attach to skill nodes), some are cross-cutting registries that are themselves close to derivable graph data (command-registry.json in particular looks like a hand-maintained shadow of what a command-carrier node scan should produce automatically).

## 3. Generated mirrors (source → `plugins/`)

Driven by `scripts/packaging_lib.py::export_plugin_tree()` (called from `scripts/export_plugin.py`, invoked by the CLI via `invoke_repo_script(repo_root, "scripts/sync_root_plugin_manifests.py", ...)` at `charness:2589`, plus `scripts/sync_support.py` for support skills). The mapping is **not** one blanket copy — it's a hardcoded list of distinct source→dest rules, each with different semantics:

| source | dest | rule |
|---|---|---|
| `README.md` | `plugins/charness/README.md` | rewritten w/ generated header + link rewriting |
| `skills/public/*/` | `plugins/charness/skills/*/` | full copy, **`public` segment collapsed** — this is the load-bearing fact `runtime_bootstrap.skill_script()` (scripts/runtime_bootstrap.py:236-250) has to special-case: it searches both `skills/public/<skill>/scripts/` (dev tree) and `skills/<skill>/scripts/` (exported tree) |
| `skills/shared/` | `plugins/charness/shared/` | verbatim replace |
| `.claude/agents/` | `plugins/charness/agents/` | host-specific relocation (source path deliberately not documented to consumers) |
| `skills/support/*` (minus `generated/` and upstream-consumed support ids) | `plugins/charness/support/*` | filtered copy + `capability.json` path rewrite |
| `profiles_dir`/`presets_dir`/`integrations_dir` (manifest-declared) | same relative path under plugin root | `replace_tree` |
| `integrations/locks/` | `plugins/charness/integrations/locks/` | `export_lock_surface` (special) |
| `scripts/` | `plugins/charness/scripts/` | full copy minus `SOURCE_ONLY_PLUGIN_SCRIPTS` |
| `runtime_bootstrap.py`, `yaml_output.py`, `skill_runtime_bootstrap.py` | plugin root | copied individually — code comments explain these are load-bearing shims that broke consumers when omitted (v6.0.0 postmortem in comments) |
| `packaging/bootstrap-python.json`, `packaging/bootstrap-requirements.txt` | `plugins/charness/packaging/` | only these two of `packaging/` are shipped |

The manifest driving field names (`source.readme`, `source.public_skills_dir`, `source.support_skills_dir`) lives in `packaging/charness.json`. A mirror-pair node/edge could be mechanically derived **only if the graph models each rule separately** — a single generic "mirrors" relation covering all of `plugins/` would misrepresent the collapse, filter, and shim-injection behavior actually present.

## 4. Packages, entrypoints, `import_repo_module`

**No installed Python package exists.** `pyproject.toml` has no `[project]`/`[build-system]` table — only `[tool.pytest]`, `[tool.ruff]`, `[tool.vulture]`. `pip show charness` confirms nothing is installed. So "package" in this repo cannot mean a PyPI/importable distribution; it must mean either (a) a skill directory, (b) the exported plugin artifact under `plugins/charness/`, or (c) nothing — #746 needs to pick one explicitly rather than assume Python-package semantics.

`./charness` (repo root, extensionless, `ruff: noqa: E402`, explicitly carved out of `PLR0915` length gating per `pyproject.toml`'s per-file-ignores comment) is the CLI entrypoint. It resolves its own runtime root via `_runtime_bootstrap_module()`, checking `EMBEDDED_REPO_ROOT` (presence of `packaging/charness.json` next to the script) vs. a managed checkout, then delegates subcommands by shelling to `scripts/*.py` via `invoke_repo_script`/`invoke_repo_json_script`.

`scripts/runtime_bootstrap.py::import_repo_module(script_file, module_name)` (line 219) is the dynamic-import backbone used pervasively across `tests/` and `scripts/`: it resolves `repo_root_from_script()`, inserts repo root onto `sys.path`, then `importlib.import_module(module_name)` — e.g. `_scripts_packaging_lib_module = import_repo_module(__file__, "scripts.packaging_lib")` in `packaging_lib.py` itself, and dozens of test files do `import_repo_module(__file__, "scripts.<x>")` instead of a plain `import scripts.x`. There's also `load_path_module()` (spec-based, path-only, no sys.path mutation) and `skill_script(repo_root, skill, name)` which is the dev/export dual-path resolver mentioned above.

## 5. Tests

`tests/` is flat-ish with a few subdirs: `coverage_debt/`, `quality_gates/`, `charness_cli/`, `control_plane/`, `agent-runtime/`, `fixtures/`. Config in `pyproject.toml`: `pythonpath = [".", "scripts"]` — so tests can do plain `from scripts.x import y` OR bare `import host_hook_*`-style names, comment warns against `scripts/<stdlib-name>.py` shadowing. Two reference styles coexist: plain imports (`from scripts.worktree_doctor_state import ...`, `import scripts.doctor as doctor_module`) and dynamic `import_repo_module(__file__, "scripts.X")` (used when the test wants export/packaging code or to avoid import-order issues, e.g. `test_quality_scaffold.py`, `test_release_changed_line_regressions.py`, `test_packaging_install_surface_orphan_dirs.py`). Many tests also shell out via `subprocess.run` to invoke `./charness` or scripts as real CLI processes (`test_web_fetch_help.py`, `test_agent_browser_runtime_guard.py`, etc.) — this is a second, separate "tests" edge kind (process invocation, not import).

A pytest marker `slow_corpus` distinguishes "pins a rule against a seeded fixture" (standing lane, fast) from "runs a real CLI over the whole repo corpus/export" (release lane) — this is itself a graph-relevant distinction: some tests exercise the mirror/export surface directly as a regression probe.

## DESIGN CONSTRAINTS (facts the typed graph MUST model correctly)

1. **Skill node identity = `SKILL.md` frontmatter `name:`**, not the directory name alone (though currently they match); `handoff` lacks a discoverable SKILL.md and needs explicit handling.
2. **Mirror-pair edges are not one uniform rule.** `export_plugin_tree()` has ~10 distinct source→dest transforms (path-collapsing, filtering by exclusion set, individual-file shim injection, host-specific relocation). A generic `mirrors` edge type needs a `transform_kind` discriminator or the graph will silently misrepresent the `public/` segment collapse and the shim-copy behavior.
3. **`skill_script()`'s dual-path resolution is load-bearing**: any node representing a skill's script must resolve under both `skills/public/<skill>/scripts/` (source) and `skills/<skill>/scripts/` (exported) — same logical script, two physical paths depending on which tree is being graphed.
4. **`import_repo_module` is a dynamic-import indirection layer**: static import-edge extraction (AST-based) will miss or need special handling for `import_repo_module(__file__, "scripts.X")` calls — the module name is a string literal argument, not a normal `import` statement, so an "imports" edge extractor must special-case this call pattern (and its sibling `load_path_module`).
5. **`./charness` is extensionless and invokes other scripts by subprocess (`invoke_repo_script`/`invoke_repo_json_script`), not by Python import** — the command-carrier → script relationship is a process-invocation edge, distinct from import edges.
6. **No installed Python package exists in this repo.** "package" nodes cannot assume PyPI/setuptools semantics; the design must define package-node meaning explicitly (skill directory? exported plugin artifact? or omit the node type).
7. **Adapters split into two populations** with different graph roles: per-skill hand-authored policy (`*-adapter.yaml`, "human policy" — attach to skill node as config) vs. cross-cutting registries that are near-mechanically-derivable shadows of other graph facts (`command-registry.json`, `cli-side-effect-probes.json`, `surfaces.json`) — treating both as the same "adapter" node type would erase this distinction that the repo itself already codified in `command-dominance.yaml`'s "single owner" comment.
8. **Test-to-production edges are two kinds**: import edges (`from scripts.x import y`, or dynamic via `import_repo_module`) and process-invocation edges (`subprocess.run(["./charness", ...])` or script-as-CLI). The `slow_corpus` marker tags tests that specifically exercise the *export/mirror surface itself* as a regression probe — relevant if #746 wants a "tests" edge that distinguishes unit-level from corpus/export-level coverage.
9. **`pythonpath = [".", "scripts"]` in `pyproject.toml`** means module resolution for tests is root-relative and `scripts/`-relative simultaneously — a naming collision hazard the repo already warns about in a comment.
