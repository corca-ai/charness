## Bump Rationale (the record's template cannot carry this)

`patch`, 6.0.0 -> 6.0.1.

`version-policy.md` requires a stated rationale whenever the level is debatable,
and this one was: the preparer proposed `minor` on the ground that the release's
one `feat` — a new export-self-sufficiency detector — makes a consumer's gate
catch cases it did not before. The release critique refuted that:

- "a gate catching more" is the literal content of the policy's Patch bullet
  "validation or packaging repairs". If it counted as minor, the patch bucket
  would be empty by construction, because every validator fix has that shape.
- None of the four registered release claim surfaces moved in this delta — no
  new JSON-declaring script, no new `charness` subcommand, no new public
  `SKILL.md`, no new `scripts/check-*.sh`. The public surface did not move.
- The detector's own author calls it a repair, not a capability.

Against `major`: nothing was renamed or removed, no install surface changed, and
no forced migration exists. The one behavior change a consumer could feel — the
debug validator's strict-vs-legacy ruleset moving from filename-keyed to
role-keyed — was MEASURED not to change any corpus verdict: on a legacy-shaped
record behind a symlinked pointer, the v6.0.0 validator and the 6.0.1 validator
both exit 1, identically. The pointer's name always applied the strict rules to
the target's bytes.

Why this is not in `charness-artifacts/release/latest.md`: that record's
template emits no bump-rationale field, and `publish_release_artifact.py`
neither accepts nor writes one. Re-running the helper cannot add it. Recording it
here is the available honest move; giving the template a field is next-session
work, named below.
