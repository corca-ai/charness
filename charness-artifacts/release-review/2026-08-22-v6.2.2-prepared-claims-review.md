## What was reviewed, and how

Three independent claims rounds ran, each in a separate bounded read-only
subagent context (`Read`/`Grep`/`Glob` only; no `Bash`, `Edit`, `Write`, or
`Agent`). Each was asked the claims question — does the RECORD survive contact
with what shipped — rather than whether the code is correct, which two code
review rounds and a release critique had already asked.

All three returned `fail`. This narrative is written after the third round's
findings were repaired.

## What held

- **Version story.** All four version-bearing surfaces read `6.2.2`
  (`packaging/charness.json`, both plugin manifests, the marketplace file), the
  checked-in plugin export carries the repaired module and registry text rather
  than a stale export, and the record claims no surface it did not touch.
- **The quality lane really passed.** Round 1 corroborated it in a second
  channel — the repo's rolling runtime-signals file, which then held both the
  165960ms failure the preparation retro describes and the 176362ms pass. That
  file is gitignored and its command table has since been overwritten, so the
  corroboration is recorded as having happened and is not reproducible from it.
  A later durability gate refused the record for citing it, which is the same
  point made mechanically.
- **`required: false` for real-host proof is honest**, not a gap: the adapter
  scopes those triggers to root-CLI and install/update/doctor/sync seams, and a
  skill script touching none of them is genuinely outside that class.
- **The `#694` over-fire disclosure repair.** Round 2 and round 3 both read the
  shipped payload and confirmed it leads with the disambiguating check.

## What did not hold, and what was done

**Round 1 — one blocker.** The record asserted "no verdict change" as flat fact
while the critique it cited as Review Proof recorded that the read establishing
it had NOT been performed — and "no verdict change" is the justification for
patch rather than minor. The read was then performed by the parent: the shipped
module and `git show v6.2.1:` of the same path, called with identical injected
dependencies over 400 constructed inputs (5 statuses x 8 cadence shapes x 5
acceptance shapes x frame present/absent), comparing `(applies, ok)` only —
**0 divergences**. Evidence:
`charness-artifacts/probe/2026-08-22-v6.2.2-cadence-verdict-differential.json`.
That probe is parent-authored and says so; it is not independent evidence.

Round 1 also found the critique recording a subagent's self-report as
`host-confirmed`, in a session that had separately recorded a subagent violating
its read-only instruction. Corrected to `reviewer-reported:`, which forced
`Host exposure state` down from `applied` to `metadata-hidden` — the artifact
validator refuses `applied` without a host confirmation, which is the validator
telling the truth about which value was wrong.

**Round 2 — the repairs carried their class.** Three of round 1's repairs
reproduced the defect they fixed:

- The `docs/handoff.md` repair replaced an outdated framing with a commit id
  that the subsequent amend orphaned, and which was unsatisfiable in principle:
  a file committed inside a commit cannot name that commit. Confirmed
  independently — `373208f9f` is a real object and is not an ancestor of `HEAD`.
  The id was removed and the reason recorded in its place.
- The over-fire qualification replaced an understatement with an overstatement,
  describing a refusal the code does not make. `check` requires BOTH a
  flag-naming cadence line and an acceptance line demanding broad proof per
  slice.
- The quality-lane qualification stated a count of "two artifacts" that the
  repair's own four new files falsified while it was being written.

Round 2 also found the qualifications appended BELOW `## Bump Rationale`,
undoing by hand a position invariant the release helper adopted after a guard was
rebuilt wrong three times. Moved above it.

**Round 3 — one structural blocker and two repairs carrying their class again.**

- **The blocker neither prior round could see:** the claims lane preserves the
  prepared blob through the tag, but the post-publish step overwrites
  `charness-artifacts/release/latest.md` from its generated payload and pushes
  it. Publishing as-is would erase every qualification from the pointer this
  repo directs later readers to. This narrative is the fix.
- The `cli_skill_surface_gate` bullet forbade reading a runtime as a verdict and
  then pointed at a file holding a *different* check's row. Corrected, and the

  aborts the prepare — this record existing is the evidence.
- The quality-lane bullet attributed 176.4s to the record's own
  `## Release Runtime` line, which says 176.795s. Both numbers now appear with
  their sources.
- The corrected over-fire bullet had dropped the polarity condition, re-opening
  the dismissal path the release critique's F1 was repaired to close. The
  condition is restored.
- The preamble's "None of these is a code defect" was falsified by the
  over-fire bullet directly beneath it. Removed.

## Standing limitations of this release

- **`6.2.2` ships a known over-fire that hard-blocks `--pursue-ready`
  activation.** It is disclosed, not fixed. A cadence line that names a deferral
  flag without deferring, beside an acceptance line demanding broad proof per
  slice, is refused as contradictory even when the artifact is truthful.
- **The `#681` repair has never been verified on any installed copy.** The
  post-publish obligation is to replay the reproduction against the installed
  `6.2.2` plugin on an `active` artifact carrying a soft-wrapped non-deferring
  cadence bullet. A `charness version` or `charness doctor` readback is not that
  branch.
- **`Evaluated changed paths: 36`** in both the record and the release
  auto-retro is stale: the differential probe was added after that census.
- **The release auto-retro asserts a publish that has not happened** and records
  `session_id: "none"` while the preparation retro beside it records session
  `2026-08-22-b-release` with five score events. Both ship in this commit; the
  auto-retro is helper-generated and says in its own body that it does not cover
  the session.
- **Nothing here proves a distinct observer existed.** Each round's context is
  recorded, and the boundary fingerprint proves the shared tree did not drift
  around them, but the distinctness signal is free text on the publishing
  machine's own side.

## Verdict

Round 3's blocker and both class-carrying repairs are corrected; the remaining
items are recorded above rather than fixed, and are limitations of what ships
rather than errors in what the record says about it.
