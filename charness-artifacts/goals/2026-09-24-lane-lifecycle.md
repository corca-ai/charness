# Achieve Goal: Lane lifecycle and orchestration ownership

Created: 2026-09-24
Planning record: mutable until Goal Binding; the binding freezes these exact bytes.

## Goal

Charness owns the multi-lane orchestration loop end to end: before a lane (brief critique, premise check, acceptance-first, base freshness, shared skeleton, size calibration), while it runs (steer, executor probe, DAG queue, report economy, decision ledger), and after it lands (self-review, typed exit codes, merge train, lesson injection, landing review, metrics, test cache, friction-driven repair). One goal closes issues 837-843 as instances of that loop instead of twelve separate mechanisms.

The previous framing (837-842 as a carrier lifecycle) is superseded: #843's eighteen practices showed the carrier is only the middle third. Fire-and-forget lanes plus private integrator scripts were the root pattern behind the last two weeks of issues (#814, #815, #816, #822, #823, #826, #827, #829, #830, #831, #833, #834, #835, #836); each fix landed on the carrier while the orchestration around it stayed tribal.

## Non-Goals

- No hosted daemon or background service; the DAG file plus ready-pull scheduling is a repo-local mechanism the integrator invokes, not a running scheduler.
- No new executors and no changes to the codex/muse CLIs themselves; executor work stays at the carrier boundary.
- No verbatim import of Ceal's `scripts/ops/lane/` prototype; decision cores are re-derived against this repo's tests.
- No release publication, version bump, or push; the release skill owns that boundary under a separate explicit request.
- No changes to already-landed fixes (#814-#836 stay as-is except where a slice explicitly migrates them onto the new envelope).

## Boundaries

- All provider mutations (parent/child issues, closes) go through the `issue` skill's Goal Run operations with exact readback; no direct `gh` writes.
- `skills/public/` stays the canonical source; `plugins/` mirror is regenerated by the parent at integration, never hand-edited.
- Test-form gates hold: topical test files per slice (800-line cap keeps new cases out of `test_task_run.py`), `run_standing_pytest.py` for execution, changed-line proof for verdict-logic edits.
- Parent worktree is user state; implementation runs in `task run` lanes with disjoint path sets; parent alone syncs, verifies, integrates.
- Docs changes ride in the touching slice; `scripts/check-docs.sh` proves the graph at integration.

## User Acceptance

- Before launch: a cheap fresh-eye brief critique runs before the expensive lane; a bounded premise-check phase reports per-item BLOCKED without blocking the whole lane on one item; critical lanes carry a committed failing acceptance skeleton the lane must turn green; a lane whose base trails its dependency tip is refused or warned; shared seams land interfaces/builders/simulators before sibling fan-out; briefs grep before creating shared primitives and declare lane size, with a split suggestion past the calibrated limit (#843-1..7).
- While running: a steered message reaches the lane transcript before its next edit and is timestamped in the result (#837); usage-limit failures report typed `executor_unavailable` with `retry_after` and `task executors` probes without starting a lane (#838); one DAG file holds the static plan (lanes/dependencies/carrier/brief) while status stays a read-through view of provider child state, launching ready dependents and pulling on freed slots (#843-8,9); lanes return a short summary while the full report lands in a file (#843-10); mid-goal decisions accumulate in one ledger linked from results, with the provider graph owning open/blocked/closed truth (#843-11).
- After landing: self-review is default-on only for lanes touching an irreversible boundary (provider close, publish/push, external writes, proof-surface/verdict-logic edits, uncertain deletions) and cheap opt-in elsewhere, carrying fixed/deferred/disputed findings; an unavailable reviewer skips cleanly and the skip is recorded as a non-claim, never as review-passed (#839); each kind maps to one documented exit code 0-5 with blocker text in a stable field (#840); one verify run lands N branches, names the first red branch, and re-queues when main moves (#841); scoped lanes receive matching ledger lessons with injected ids in the result (#842); every fast-forward starts a non-blocking fresh-eye review of the landed range (#843-12); per-lane/per-carrier metrics and a content-addressed test cache cut re-verification, and a cache skip never asserts completion (#843-13,14).
- Learning loop: every block/relaunch/conflict/premise failure appends to a friction log with repeat escalation; long runs carry periodic retros and a fixed improvements line; orchestration pointers re-inject after compaction; lane guidance states the environment-includes-agent principle (#843-15..18).
- No slice reintroduces a relaunch where the loop offers resume: scope-amend re-validates the same candidate (#831/#834 stay fixed).

## Agent Verification Plan

### Low-Cost Checks

- Focused pytest per slice via `python3 scripts/gates_support/run_standing_pytest.py --repo-root . --pytest-target <topical-file>`; new cases in topical siblings, never in the capped core file.
- Tokei caps (`REPO_SCRIPT_FILE_MAX=480`, test 800) checked before each slice integration; split modules rather than growing `task_run.py`.

### High-Confidence Checks

- Changed-line/mutation proof for verdict-logic edits (state derivation, exit mapping, premise verdicts, cache skip decisions) per the operating contract's proof-surface class.
- `scripts/check-docs.sh` over help text, result schema, DAG schema, and new command surfaces in the touching slice.
- One full read-only lane after parent integration, before any broad lane; plugin mirror export precedes it.

### External or Live Proof

- Provider roundtrips only: parent/child reads and guarded closes through the `issue` backend; exact readback decides completion, never local state.
- Deterministic fixture lanes; executor-behavior claims stay non-claims unless a fixture executes them. Named fixtures: fake-executor usage-limit string (WI-2), 2-lane DAG fixture with mocked provider child state (WI-8b), compaction pointer-file fixture (WI-11), stub fast-forward fixture (WI-7 trigger half), time-boxed brief critique with recorded duration instead of a "2-minute" claim (WI-4). Any acceptance bullet without a named fixture is a non-claim.

## Dependency Strategy

Speed-versus-conflict policy: run WI-1 first and alone (small, fast, unblocks the hard frontier); WI-10a starts immediately alongside it (disjoint files); then fan the rest out with disjoint test files and accept merge conflicts in shared `scripts/task_run/` modules, resolved by the parent at integration. Mid-run edge changes go through operator-approved dependency amendments, not prose. Edge suffixes: `~soft` means parallel-safe with reconcile-at-merge; `~gate` means the gated half starts only after the named slice lands (it never blocks early design work, only integration of that half).

- WI-1 emits two frozen interfaces: the kind/exit vocabulary and friction/ledger event-schema v1 that WI-9/WI-11 consumers read.
- WI-2 → WI-1 hard: fallback reporting has no vocabulary without the kind enum and exit mapping.
- WI-3 → WI-1 hard: steer accept/nack dispositions are recorded in the typed envelope.
- WI-4 → WI-1 hard: per-item BLOCKED verdicts are kinds, not prose.
- WI-7 → WI-1 hard (self-review half extends the envelope) + WI-8a~gate (landing-trigger half starts after the train lands; verified standalone with a stub fast-forward fixture).
- WI-5, WI-6, WI-8a, WI-8b, WI-9 → WI-1 soft: each builds on existing vocabulary and reconciles with the extension at merge; parallel-safe. WI-6 → WI-3 soft: shared `task_run_lane_runner.py` edits merge, not block. WI-5 → WI-8b soft: only the skeleton-ordering half reads the DAG. WI-8b → WI-8a soft: DAG reuses the train's outcome vocabulary. WI-8b stays a pure function plus a single-shot pull command: no watch loop, background poll, or daemon, ever.
- WI-10a: no edges, parallel-safe. WI-10b → WI-1~gate + WI-8a~gate: the skip decision reads the frozen codes and verify outcomes.
- WI-11 → WI-1 soft (result and event-schema shapes) and WI-6 soft (prompt-assembly shape); event-schema ownership stays with producing slices, which emit WI-1's frozen v1.
