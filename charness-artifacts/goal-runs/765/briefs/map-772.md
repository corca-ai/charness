### 3.5 LIVE FINDING: the exported `run-quality.sh` fails without a gate-named refusal

This is a real defect on #772's own scope, observed in the throwaway environment:

```
$ cd $SB/consumer
$ bash "$HOME/.codex/plugins/charness/scripts/run-quality.sh" --read-only
.../plugins/charness/scripts/run-quality.sh: line 126: .../plugins/charness/.githooks/runtime-env.sh: No such file or directory
exit=1
```

Why: `scripts/exported-copy-guard.sh:102-122` only refuses when `git rev-parse --show-toplevel` names a toplevel that differs from the script's package root. In a genuinely installed export at `~/.codex/plugins/charness` there is **no git repo at all**, so `git_toplevel` is empty, the guard takes its documented "nothing is claimed" branch (`exported-copy-guard.sh:27-30,123-126`), `REPO_ROOT_VERIFIED` stays 0, and the runner proceeds — then dies at `scripts/run-quality.sh:128` sourcing `.githooks/runtime-env.sh`, which is not in the export.

This is exactly the diagnostic-quality regression the guard's own comment says it exists to prevent (`exported-copy-guard.sh:51-54`: "a relocated, symlinked or PATH-resolved gate refuses BY NAME instead of dying on a bash `No such file or directory`"). The guard's test (`tests/quality_gates/test_shell_gate_root_resolution.py`) asks a membership question, not this behavioural one. Recommend this becomes either a #769 fix or a recorded non-claim on the #772 packet.

Secondary observation: the quality planner prints `command: ./scripts/run-quality.sh --read-only` for its `read-only-quality` gate packet even in a fresh consumer repo that has no such file. The catalog does carry `run_when: repo exposes this repo-native command or an equivalent standing quality gate` (`skills/public/quality/references/catalog.yaml:133`), so the contract is right, but the printed plan does not surface the gate as inapplicable.
