## 1. Import mechanics today

### 1.1 `import_repo_module` resolution

`/home/hwidong/codes/charness/scripts/runtime_bootstrap.py:219-224`:

```python
def import_repo_module(script_file: str | Path, module_name: str) -> ModuleType:
    repo_root = repo_root_from_script(script_file)
    repo_root_text = str(repo_root)
    if repo_root_text not in sys.path:
        sys.path.insert(0, repo_root_text)
    return importlib.import_module(module_name)
```

Three steps: derive the repo root from the *calling script's* path, put that root on
`sys.path`, then hand the name to `importlib.import_module`. The dotted-name support
the issue asks for is entirely inside `importlib.import_module` and already present.
The fragile step is the first one.

`/home/hwidong/codes/charness/scripts/runtime_bootstrap.py:209-216`:

```python
def repo_root_from_script(script_file: str | Path) -> Path:
    override = os.environ.get("CHARNESS_REPO_ROOT")
    if override:
        root = Path(override).expanduser().resolve()
    else:
        root = Path(script_file).resolve().parent.parent
    configure_runtime_environment(root)
    return root
```

`parent.parent` hard-codes the depth `<repo>/scripts/<name>.py`. It is the single
highest-blast-radius flat assumption in the repo.

### 1.5 `pyproject.toml` pythonpath

`/home/hwidong/codes/charness/pyproject.toml:3-8`:

```toml
# Put the repo root and scripts/ on sys.path for the test session so test
# modules import `scripts.x` / bare `host_hook_*` at the top instead of each
# file re-doing a `sys.path.insert(...)` bootstrap (which forced `# noqa: E402`).
# Caution: with scripts/ on the path, a scripts/<stdlib-name>.py would shadow
# that stdlib module during tests — keep script basenames non-colliding.

```

Two consequences for #770.

- The comment's caution is **understated in two ways**: the hazard is not only stdlib
  and not only *file* basenames. `scripts/` on `sys.path` means any
  `scripts/<dirname>/` becomes an importable top-level package. See §2.5.
- Because `"scripts"` is on the test-session path, **a nested script's bare
  `from runtime_bootstrap import ...` keeps working under pytest**. The test suite
  will stay green while `python3 scripts/<pkg>/<name>.py` is broken. This is the
  central trap in #770: the standing lane cannot see the breakage.

Also `/home/hwidong/codes/charness/pyproject.toml:59` —
`[tool.vulture] paths = [..., "scripts", ...]` passes the directory, so vulture
recurses and is safe.
`/home/hwidong/codes/charness/pyproject.toml:56` per-file-ignore keys on `"charness"`
only, unaffected.

Current stdlib-shadowing check: **zero** `scripts/*.py` collide with
`sys.stdlib_module_names`, and zero `skills/**/scripts/*.py` do either.

### 5.3 Does `check_plugin_import_smoke.py` import subpackage modules?

**Yes, by `rglob`, and it is the one gate that would catch a nested-import break —
but only by luck of sort order.**

`/home/hwidong/codes/charness/scripts/check_plugin_import_smoke.py:25-26` delegates to
`smoke_exported_plugin_imports`
(`/home/hwidong/codes/charness/scripts/validate_packaging_install_surface.py:221-240`),
which runs `/home/hwidong/codes/charness/scripts/templates/plugin_import_smoke.py.txt`
as a subprocess. That template:

```python
plugin_root = pathlib.Path(sys.argv[1])
sys.path.insert(0, str(plugin_root))            # :4
for py_path in sorted(plugin_root.rglob("*.py")):   # :6  -- recursive
    parent = str(py_path.parent)
    if parent not in sys.path:
        sys.path.insert(0, parent)              # :9-11
    module_name = "smoke_" + str(rel).replace("/", "_")...   # :13
```

`:6` is `rglob`, so nested packages **are** exercised. `:9-11` inserts each file's own
parent directory, so a nested module's bare `from runtime_bootstrap import ...`
resolves via *either* the root shim at `plugin_root/runtime_bootstrap.py` (`:4` put
`plugin_root` on the path) or `plugin_root/scripts` once some flat `scripts/*.py` has
been visited.

**The fragility:** which of those two happens depends on `sorted()` order. Files sort
lexicographically, and `_` (0x5F) sorts before every lowercase letter, so a package
named `_lib` would be walked **before** any flat `scripts/*.py` has put
`plugin_root/scripts` on the path. In that window only the root shim saves it — and
the root shim covers exactly three names (`runtime_bootstrap`, `yaml_output`,
`skill_runtime_bootstrap`). A nested module importing any *other* bare sibling
(`adapter_lib`, `quality_label_universe`, `check_doc_links`, `mutation_recovery`, …)
fails. That is 12 or so of the 262 bare imports, and they are exactly the non-obvious
ones. Note that `#769` moves `validate_packaging_install_surface` to `tools/`, so the
smoke gate itself lands in `tools/` while the template stays in `scripts/templates/`.

Also `SystemExit` is swallowed (`:21-22`) and every other exception is collected
(`:23-24`), so this gate reports import errors as a list rather than a traceback.

### 5.4 Does the installed-consumer bootstrap resolve `scripts.<pkg>.<name>`?

Partially, and the failure is the silent kind.

- **Dotted resolution: yes.** `import_repo_module` → `importlib.import_module` handles
  arbitrary depth (§1.1, probe C/D), and the root shim re-exports it verbatim
  (`runtime_bootstrap.py:22`). `scripts/__init__.py` already exists; each new package
  needs its own `__init__.py` for a regular package, though probe D shows namespace
  packages resolve too.
- **Repo-root resolution: no.** The shim re-exports `repo_root_from_script`
  (`runtime_bootstrap.py:24`), which is still `parent.parent`
  (`scripts/runtime_bootstrap.py:214`). In an installed tree a nested script gets
  `plugins/<pkg>/scripts` as its "repo root" instead of `plugins/<pkg>`, with no error
  (probe F).
- **Skill-side resolution: yes, and depth-agnostic** — `repo_root_from_skill_script`
  walks ancestors for the `scripts/adapter_lib.py` marker
  (`scripts/skill_runtime_bootstrap.py:118-120`), which works at any depth **provided
  `adapter_lib.py` stays at `scripts/` top level**.
- **Direct execution of a nested script: no.** Probe E: even with the root shim
  present, `python3 scripts/gates/check_probe.py` raises
  `ModuleNotFoundError: No module named 'runtime_bootstrap'`, because `sys.path[0]` is
  `scripts/gates`. Every documented `python3 scripts/<pkg>/<name>.py` carrier
  (§3) is broken until the preamble changes.

### 5.5 The mechanical consequence for #770's commit plan

The issue plans "one package per commit". That is only safe if the preamble problem is
solved **first**, in its own commit, because every package move drags 185 files' worth
of the same broken preamble. Two viable fixes, in order of preference:

1. **Fix `repo_root_from_script` to find the root by marker walk**, mirroring
   `repo_root_from_skill_script` (`scripts/skill_runtime_bootstrap.py:98-123`) instead
   of counting `parent.parent`, and replace the bare `from runtime_bootstrap import …`
   preamble with the ancestor-walking shim already machine-enforced for skill scripts
   (`check_bootstrap_shim_consistency.py:33-38`). This makes depth irrelevant
   everywhere and reuses a pattern the repo already gates.
2. Add a `sys.path` bootstrap line to every moved file. Cheaper per file, but it
   re-introduces the `# noqa: E402` pattern `pyproject.toml:3-5` says the pythonpath
   setting exists to avoid.

Either way the ordering is: preamble fix → `--files` snapshot flag (§4.6) → FLAT-pattern
repairs (§3.3, §4.3) → then one package per commit.
