# Resolution Brief — corca-ai/charness#449

**Classification**: feature (closed as decision-needed; see Decision below)

**Reporter JTBD**: after a publish, get an observer with a different machine
and credential identity to read back the public release surface and record
its verdict durably, so publication proof does not depend solely on the
publisher's own environment.

**Proposed boundary** (as drafted, before the decision below):
- in scope: a new GitHub Actions workflow on `release: types: [published]`
  that independently fetches the public release/tag using the Actions
  runner's own machine and `GITHUB_TOKEN` identity, and persists a durable
  record
- out of scope: redesigning the existing local
  `charness-artifacts/probe/<date>-<tag>-release-observer.json` observer or
  its `unauthenticated-http` channel

**Open decisions and proposed resolutions** (all three named by the issue):
1. Trigger form — proposed `release: types: [published]`.
2. Record destination/retention — proposed a permanent commit comment on the
   release's target commit via the GitHub Commits API (discoverable from the
   commit/tag page, no retention expiry unlike workflow-run artifacts).
3. Cross-link with the local probe artifact — proposed deriving the link
   from the shared commit SHA already present in both records, rather than
   requiring either side to write a pointer back to the other.

**Non-goals**:
- not redesigning release-proof plumbing beyond this one gap

**Acceptance checks** (as drafted):
- a published release has a durable post-publication record whose observer
  identity is machine- and credential-distinct from the publisher

**Open decisions**: non-empty (trigger form, record destination/retention,
cross-link mechanism) — per `resolution-brief.md`, this forces a pause
regardless of the adapter's `feature_brief_pause` default.

**Autonomous vs pause**: paused for user discussion. Confirmed record
destination (commit comment) with the operator, then raised the follow-on
question of granting the new CI workflow commit-comment write permission
(a new class of write surface — every existing workflow in this repo is
read-only). The operator then asked why this is needed at all and decided
not to pursue it.

## Decision

The operator (repo owner) decided **not to implement** this feature. Given
the added complexity of a new CI workflow, a new GitHub Actions write-
permission surface (every existing workflow — `mutation-tests.yml`,
`quality-core.yml` — is read-only; this would be the first that posts
back to GitHub), and a new observer-record schema, against the marginal
value over the existing local `unauthenticated-http` distinct-channel
observer, the operator judged this was not worth building right now for
this repo's actual threat model and scale.

This is a product/scope decision, not a technical blocker — nothing here
prevents implementing it later if the operator's judgment changes (for
example, if the publisher-environment-compromise scenario the issue
describes becomes a real, not theoretical, concern).
